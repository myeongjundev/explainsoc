# ExplainSOC 설계 — 성능표에 없는 질문

> 상태: 사용자 승인 완료 · Claude 구현 인계
> 작성일: 2026-09-21
> 승인일: 2026-09-21
> 범위: 마지막 과제 B의 구현 기준을 고정한다. 변경이 필요하면 구현보다 먼저 이 문서를 갱신한다.

---

## 0. 설계 결론

ExplainSOC는 보안 AI 모델을 합격·불합격으로 판정하는 도구가 아니다. 제품 소개서나 평가표에
적힌 숫자 한두 개를 받은 주니어 보안 담당자가 **그 숫자가 말하지 않는 평가 조건을 찾고,
공급자에게 바로 물을 질문을 준비하는 도구**다.

앱의 서명 장면은 다음 반전이다.

```text
정확도 0.6299 · 오탐률 0.0002
                 ↓
겉으로는 무난해 보이는 성능 주장
                 ↓
공격 220,788건 가운데 탐지 160건
                 ↓
모든 흐름을 정상으로 예측한 기준선 정확도 약 0.6297
                 ↓
“시험에 학습 때 없던 공격이 들어 있었습니까?”
```

정확도 0.6299, FPR 0.0002, 시험 공격 220,788건과 탐지 160건은 논문 V-2의 미관측
공격 XGBoost 결과다. 항상 정상 기준선 약 0.6297은 원고 IV-3의 시험 정상 375,518건을
시험 전량 596,306건으로 나눈 **화면 설명용 파생값**이다. 논문의 새 결과나 일반 임계값으로
부르지 않는다.

기존 Evidence Gate라는 이름은 쓰지 않는다. `Gate`는 앱이 모델을 승인하거나 거절하는 것처럼
읽힌다. 제품 이름은 **ExplainSOC**, 화면 설명 이름은 **성능표에 없는 질문**으로 둔다.

## 1. 누구를 돕고 무엇을 남기는가

### 1-1. 사용자가 들고 오는 것

주 사용자는 보안 AI 도입을 처음 맡은 주니어 보안 담당자다. 이 사람은 대개 다음 중 일부만
들고 온다.

- 제품 소개서의 Accuracy, Macro F1, 공격 Recall, FPR 한두 개
- “가장 높은 성능”, “낮은 오탐”, “설명이 안정적” 같은 주장
- 평가 조건은 모르거나 공급자에게 물어보지 않은 상태

혼동행렬과 데이터 분할 문서를 모두 가진 사용자를 정상 경로로 가정하지 않는다. **모름이 가장
중요한 입력**이다.

### 1-2. 사용자가 들고 나가는 것

- 입력한 숫자가 직접 말해 주는 범위
- 빠졌거나 알 수 없는 평가 조건
- 과장 없이 읽기 위한 해석 주의점
- 실제 PoC 자리에서 소리 내어 읽을 수 있는 공급자 질문
- 각 질문이 나온 논문의 절과 원문 근거

앱은 신뢰 점수, 등급, 배포 가능 판정, 모델 추천을 남기지 않는다.

## 2. 카드 1 확정 내용

### 2-1. 앱 한 문장 — BRB-C01

> 보안 AI 도입을 처음 맡은 주니어 보안 담당자가 제품 소개서의 성능 숫자 한두 개를
> 받았을 때, 이 앱이 무작위 분할 XGBoost의 Macro F1 0.9979가 미관측 공격 스트레스
> 테스트에서 0.3871로 하락한 논문 결과를 근거로 그 숫자가 말하지 않는 평가 조건과
> 클래스별 오류를 드러내고, 공급자에게 바로 물을 질문을 만들어 준다.

- 돕는 사람: 보안 AI 도입을 처음 맡은 주니어 보안 담당자
- 앱이 하는 일: 빠진 평가 조건과 클래스별 오류를 드러내고 질문으로 바꾼다
- 쓰는 논문 결과: 원고 V-2·VII의 XGBoost Macro F1 `0.9979 → 0.3871`

### 2-2. 사용자가 할 일 세 가지 — BRB-C02

1. 받은 성능 숫자 하나를 적거나 **논문 예시로 60초 검토**를 선택한다.
2. 분할 방식, 미관측 공격 포함 여부, 중복 제거 여부에 `예 / 아니오 / 모름`으로 답한다.
3. 숫자가 말하는 것과 말하지 않는 것을 확인하고 공급자에게 물을 질문을 복사한다.

## 3. 제품 원칙

### 3-1. 첫 10초에는 한 가지만 말한다

첫 화면은 “좋아 보이는 보안 AI 숫자도 평가 조건이 빠지면 다르게 읽힐 수 있다”만 말한다.
SHAP, Jaccard, 데이터 감사, 모델 세 개를 첫 화면에 함께 설명하지 않는다.

### 3-2. 모름을 실패로 취급하지 않는다

분할과 중복 제거를 모르는 사용자가 이 앱을 가장 필요로 한다. 빈 답을 오류로 막지 않고
공급자에게 물을 질문으로 바꾼다.

### 3-3. 입력한 값과 확인한 사실을 구분한다

`확인됨`이라는 표현은 쓰지 않는다. 결과 상태는 다음 세 가지다.

- **입력한 근거** — 사용자가 제공한 값이라는 뜻이다
- **확인 필요** — 정보가 없거나 모름이라고 답했다
- **해석 주의** — 숫자는 있지만 단독 해석이 위험하다

어느 상태도 모델 품질 보증을 뜻하지 않는다.

### 3-4. 논문보다 한 발짝 더 말하지 않는다

사용자 입력을 논문 수치와 우열 비교하지 않는다. 임계값을 만들지 않고, 낮음·높음·안전함·
위험함을 자동 판정하지 않는다. 논문의 사례와 확인 방법을 보여 준다.

### 3-5. 입력은 브라우저 밖으로 나가지 않는다

런타임 AI, 백엔드, 분석 스크립트, 광고, 추적 도구를 붙이지 않는다. 입력값은 메모리에만 두고
URL, 쿠키, `localStorage`에 넣지 않는다. 새로 고치면 사라진다.

### 3-6. 차별화는 기능 수가 아니라 근거 연결에서 만든다

질문마다 `왜 묻는가 → 논문 원문 → 이 연구의 한계`를 따라갈 수 있게 한다. 논문 예시의
주장 뒤집기, 항상 정상 기준선, 9종 대 3종 분할 그림이 시각적 중심이다.

## 4. 첫 화면 문구 — BRB-C03

### 4-1. 첫 10초 문구

- 제품명: **ExplainSOC**
- 제목: **그 99%, 무엇을 시험한 점수입니까?**
- 도움 한 문장: **보안 AI 도입을 처음 맡은 담당자가 성능표에서 빠진 평가 조건을 찾고,
  공급자에게 물을 질문을 논문 근거와 함께 준비하도록 돕습니다.**
- 주 버튼: **논문 예시로 60초 검토**
- 보조 버튼: **내 성능표 검토**
- 개인정보 안내: **입력한 성능 자료는 이 브라우저 안에서만 계산되며 저장하거나 전송하지
  않습니다.**

### 4-2. 반드시 보이는 논문 제목

첫 화면의 버튼 아래에 다음을 축약하지 않고 표시한다.

> 반영한 논문 · 데이터 분할 방식에 따른 XAI 기반 네트워크 침입 탐지 성능과 설명 안정성 분석

논문 저장소와 PDF 링크는 새 탭으로 열고 외부 링크임을 접근 가능한 이름에 포함한다.

## 5. 60초 안의 핵심 경험 — BRB-C03·C05

| 시간 | 사용자가 보는 것 | 제품이 증명하는 것 |
|---:|---|---|
| 0~10초 | 제목, 도움 한 문장, 논문 제목 | 누구를 어떻게 돕는지 안다 |
| 10~15초 | `논문 예시로 60초 검토` 선택 | 설명 없이 시작한다 |
| 15~30초 | 정확도·FPR 카드가 공격 탐지 개수로 뒤집힌다 | 숫자의 착시를 직접 본다 |
| 30~40초 | 학습 공격 9종 대 시험 공격 3종, 겹침 0 | 왜 같은 점수를 확대하면 안 되는지 본다 |
| 40~50초 | `입력한 근거 / 확인 필요 / 해석 주의` | 앱이 보증하지 않음을 안다 |
| 50~60초 | 공급자 질문 목록과 근거, `질문 복사` | 실제 다음 행동을 얻는다 |

이 흐름을 사용성 검증에서 실제로 재고, 60초를 넘으면 고급 설명부터 덜어낸다.

## 6. 화면 구조와 흐름 — BRB-C05

별도 라우트가 많은 대시보드 대신 한 페이지 안의 단계형 작업대로 만든다. 뒤로 가도 입력을 잃지
않고, 현재 단계와 전체 세 단계를 항상 표시한다.

### 화면 A. 첫 화면

**목적:** 누구를 어떻게 돕는지 10초 안에 전달한다.

- 4절의 첫 화면 문구
- 논문 결과를 단정이 아니라 질문으로 표현한 짧은 시각 요소
- `논문 예시로 60초 검토`, `내 성능표 검토`
- 브라우저 안에서만 처리한다는 개인정보 안내
- 입력 폼과 긴 연구 한계는 아직 보여 주지 않는다

### 화면 B. 받은 주장 입력

**목적:** 사용자가 가지고 있는 최소 정보부터 받는다.

#### 기본 입력

- 지표 종류: Accuracy / Macro F1 / 공격 Recall / FPR
- 지표 값: 0부터 1까지의 비율
- `지표 하나 더`로 필요한 만큼 추가
- 주장 선택: `가장 좋은 모델이라고 소개했다` — 예 / 아니오 / 모름

모르는 지표를 억지로 채우게 하지 않는다. 혼동행렬을 가진 사용자는 `혼동행렬로 입력`을
선택한다.

#### 혼동행렬 입력

네 개의 작은 칸을 단순히 TN·FP·FN·TP 순으로 늘어놓지 않는다. 2×2 표에 행은 **실제**, 열은
**예측**으로 표시하고 각 칸에 한국어를 함께 쓴다.

| | 예측 정상 | 예측 공격 |
|---|---:|---:|
| 실제 정상 | 정상→정상 (TN) | 정상→공격, 오탐 (FP) |
| 실제 공격 | 공격→정상, 미탐 (FN) | 공격→공격 (TP) |

양성 클래스가 공격임을 표 위에 명시한다. 입력 즉시 Accuracy, 공격 Recall, 정상 Recall,
FPR, Macro F1을 계산하되 계산 결과를 품질 판정으로 바꾸지 않는다.

### 화면 C. 평가 조건 세 질문

**목적:** 논문이 발견한 핵심 조건을 사용자의 말로 묻는다.

1. **시험 자료는 어떻게 나눴습니까?**  
   무작위 / 학습에 없던 공격을 따로 시험 / 다른 방식 / 모름
2. **시험에 학습 때 없던 공격이 들어 있었습니까?**  
   예 / 아니오 / 모름
3. **중복과 학습·시험 사이의 같은 행을 제거했습니까?**  
   예 / 아니오 / 모름

전문용어 설명은 질문 옆 도움말로 두고 답하기 전에 읽도록 강요하지 않는다.

### 화면 D. 주장 뒤집기

**목적:** 숫자를 운영 의미로 바꾸는 핵심 장면을 보여 준다.

논문 예시에서는 다음 순서를 고정한다.

1. `Accuracy 0.6299`, `FPR 0.0002`를 먼저 보여 준다.
2. `공격 220,788건 중 탐지 160건`, `미탐 220,628건`으로 바꿔 보여 준다.
3. `항상 정상 기준선 약 0.6297`과 Accuracy를 같은 축에서 비교한다.
4. “이 비교는 CICIDS2017 미관측 공격 스트레스 테스트의 시험 구성에 한정된다”고 바로 쓴다.

사용자 입력에는 혼동행렬이 있을 때만 개수 번역과 항상 정상 기준선을 계산한다. 지표 하나만
입력했다면 없는 개수를 추정하지 않는다.

### 화면 E. 논문의 실제 분할 그림

**목적:** SplitLens의 시각적 힘을 논문 범위 안에서 사용한다.

- 왼쪽: 월~목 학습 공격 9종
- 오른쪽: 금요일 시험 공격 3종
- 가운데: `공격 유형 겹침 0`
- 아래: “수집 날짜와 공격 유형 변화가 함께 바뀌었으므로 순수 시간 일반화가 아니라 미관측
  공격 스트레스 테스트다.”

사용자가 공격 유형을 추가하거나 임의 분할을 판정하는 기능은 넣지 않는다.

### 화면 F. 결과와 질문

**목적:** 분석이 아니라 다음 행동을 준다.

- 입력한 근거
- 확인 필요
- 해석 주의
- 공급자 질문 목록
- 각 항목의 `논문 근거 보기`
- `질문 복사`
- `입력 수정`, `처음부터`

질문 복사는 사용자가 입력한 비밀 숫자를 포함하지 않고 질문 문장만 복사한다. 복사 성공은
텍스트와 `aria-live`로 알린다.

### 화면 G. 연구 범위와 근거

**목적:** 긴 설명을 핵심 흐름 밖에서 확인하게 한다.

- 논문 수치와 원문
- CICIDS2017 한 데이터셋에 한정된다는 점
- SHAP과 실제 SOC 평가에 대한 경계
- 논문 저장소·PDF
- “이 앱이 하는 말 / 하지 않는 말”

## 7. 판독 규칙 — BRB-C04

규칙은 순수 TypeScript 함수와 데이터 표로 구현한다. 규칙 ID, 입력 조건, 결과 문구, 질문,
논문 근거를 한 객체에 둔다. 임계값 기반 등급은 만들지 않는다.

| ID | 입력 조건 | 화면 안내 | 공급자 질문 | 논문 근거 |
|---|---|---|---|---|
| R01 | 분할이 무작위 | 해석 주의: 관측한 공격이 섞인 시험의 높은 점수를 미관측 공격 성능으로 확대할 수 없다 | 학습에 없던 공격만 따로 둔 시험 결과도 있습니까? | VII·S1, V-2 |
| R02 | 분할이 모름 | 확인 필요: 점수를 만든 시험 조건을 알 수 없다 | 학습과 시험 자료를 어떤 기준으로 나눴습니까? | VII·S1, IV-3 |
| R03 | Accuracy는 있으나 공격 Recall과 혼동행렬이 없음 | 해석 주의: 전체 정확도만으로 공격 미탐을 알 수 없다 | 공격 Recall과 TN·FP·FN·TP를 제공할 수 있습니까? | VI-3·S3 |
| R04 | FPR은 있으나 공격 Recall이 없음 | 해석 주의: 낮아 보이는 오탐률만으로 공격 탐지 능력을 알 수 없다 | 같은 시험에서 공격 Recall은 얼마입니까? | V-2·S5 |
| R05 | `가장 좋은 모델` 주장이고 한 분할 결과만 있음 | 확인 필요: 분할에 따라 모델 순위가 달라질 수 있다 | 다른 분할에서도 같은 모델이 가장 높았습니까? | V-2·S6 |

| R08 | 미관측 공격 포함이 아니오 | 입력한 근거: 이 시험은 학습에서 보지 못한 공격을 직접 검증하지 않았다 | 미관측 공격만 별도로 둔 스트레스 테스트가 있습니까? | VII·S1 |
| R09 | 미관측 공격 포함이 모름 | 확인 필요: 새 공격을 시험했는지 알 수 없다 | 시험에 학습 때 없던 공격 유형이 들어 있었습니까? | IV-3, VII·S1 |
| R10 | FPR과 공격 Recall이 모두 있음 | 입력한 근거: 두 값을 나란히 제시한다. 높고 낮음을 자동 판정하지 않는다 | 필요하면 혼동행렬 원수치를 제공할 수 있습니까? | VI-3·S3 |

## 9. 혼동행렬 계산

양성 클래스는 ATTACK이다. 입력 원수로 다음을 계산한다.

```text
total = TN + FP + FN + TP
Accuracy = (TN + TP) / total
공격 Recall = TP / (TP + FN)
정상 Recall = TN / (TN + FP)
FPR = FP / (FP + TN)
공격 Precision = TP / (TP + FP)
정상 Precision = TN / (TN + FN)
공격 F1 = 2 × 공격 Precision × 공격 Recall / (공격 Precision + 공격 Recall)
정상 F1 = 2 × 정상 Precision × 정상 Recall / (정상 Precision + 정상 Recall)
Macro F1 = (공격 F1 + 정상 F1) / 2
항상 정상 기준선 Accuracy = (TN + FP) / total
```

분모가 0이면 0으로 만들지 않고 `계산할 수 없음`을 반환한다. 계산 결과는 화면에서 최대 소수
넷째 자리까지 보이되 테스트는 반올림 전 값을 검증한다.

## 10. 입력 검증과 실패 처리 — BRB-C05

오류는 앱 전체를 막지 않고 해당 칸 가까이에 무엇이 잘못됐고 어떻게 고칠지 표시한다.

| 입력 | 잘못된 경우 | 처리와 문구 |
|---|---|---|
| 선택 지표 | 선택하지 않음 | 숫자 칸을 열지 않고 “먼저 지표 이름을 골라 주세요” |
| 비율 | 빈 칸 | 허용한다. `정보 없음`으로 질문을 만든다 |
| 비율 | 숫자가 아닌 글자 | 계산에서 제외하고 “0부터 1 사이의 숫자로 적어 주세요” |
| 비율 | 음수 | 계산에서 제외하고 “비율은 0보다 작을 수 없습니다” |
| 비율 | 1 초과 | 계산에서 제외하고 “비율은 0부터 1 사이로 적어 주세요. 99%는 0.99입니다” |
| 비율 | NaN·Infinity | 계산에서 제외하고 일반 숫자 입력을 안내한다 |
| 혼동행렬 | 빈 칸 | 해당 값만 `정보 없음`; 네 칸 계산은 시작하지 않는다 |
| 혼동행렬 | 글자·소수·음수 | “0 이상의 정수로 적어 주세요” |
| 혼동행렬 | 안전 정수 초과 | “지원 범위보다 큰 값입니다” |
| 혼동행렬 | 네 칸의 합이 0 | “평가한 항목이 없어 지표를 계산할 수 없습니다” |
| 혼동행렬 | `TP+FN=0` | 공격 Recall을 `계산할 수 없음`; 공격 표본이 없다고 설명한다 |
| 혼동행렬 | `FP+TN=0` | FPR·정상 Recall을 `계산할 수 없음`; 정상 표본이 없다고 설명한다 |
| 평가 조건 | 미선택 | `모름`과 동일하게 질문을 만들되, 제출 전 선택을 요구하지 않는다 |
| 붙여넣기 | 쉼표 포함 숫자 | 쉼표와 양끝 공백을 안전하게 제거해 정수로 읽는다 |
| 텍스트 | HTML·스크립트 문자열 | React 텍스트로만 렌더링하고 HTML 삽입 API를 쓰지 않는다 |

오류가 있어도 나머지 유효한 입력으로 질문 목록을 만든다. 잘못된 값을 0으로 바꾸지 않는다.

## 12. 시각·상호작용 설계

### 12-1. 시각 언어

보안 관제 대시보드를 그대로 복제하지 않는다. 어두운 배경에 표를 빽빽하게 놓는 대신, 한 장의
성능 주장 문서가 검토되며 층이 벗겨지는 모양을 사용한다.

- `주장`: 중립 표면
- `입력한 근거`: 파랑 + 문서 아이콘
- `확인 필요`: 호박색 + 물음표 아이콘
- `해석 주의`: 자홍/적색에 의존하지 않는 빗금 + 주의 아이콘
- 모든 상태는 색, 아이콘, 텍스트를 함께 쓴다

숫자 축은 0부터 시작한다. `0.9974`와 `0.0007`을 같은 축에 놓을 때 작은 값에 `220,788건 중
160건`을 함께 써 0으로 오해하지 않게 한다. 작은 차이를 확대하는 잘린 축을 쓰지 않는다.

### 12-2. 반응형

- 375px부터 가로 스크롤 없이 사용한다
- 2×2 혼동행렬은 모바일에서도 2×2를 유지하되 설명은 짧게 접는다
- 질문 복사와 다음 단계 버튼은 엄지로 누를 수 있는 크기를 확보한다
- 데스크톱에서는 입력과 결과를 나란히, 모바일에서는 입력 다음 결과 순서로 둔다
- 고정 하단 버튼이 오류 문구나 마지막 질문을 가리지 않게 안전 영역과 본문 여백을 둔다

### 12-3. 접근성

- 모든 입력에 보이는 `<label>`을 둔다
- 단계 이동, 오류 요약, 복사 결과는 스크린 리더로 전달한다
- 상태를 색으로만 구분하지 않는다
- 키보드만으로 예시 실행, 입력, 결과 확인, 질문 복사가 가능해야 한다
- 모션 감소 설정에서는 카드 뒤집기를 즉시 전환으로 바꾼다
- 수치 표와 시각화에 같은 내용을 담은 텍스트 대안을 둔다
- 포커스가 보이고 모달을 쓰지 않는다

ID만 참조한다. 화면 컴포넌트에 논문 숫자와 판독 문구를 흩어 쓰지 않는다.

규칙 하나에는 최소 다음이 들어간다.

```text
id · 조건 함수 · 상태 · 제목 · 설명 · 질문 · evidenceIds
```

판독 순서는 위험 점수가 아니라 사용자 행동 순서로 고정한다. `확인 필요 → 해석 주의 → 입력한
근거` 순서로 보여 주고 자동 점수는 계산하지 않는다.

## 23. 대표 앱 V2 — PoC 검토 작업대

> 승인일: 2026-09-22
> 배경: 사용자는 과제 제출용 설명 앱이 아니라 포트폴리오 대표 앱으로 확장하기로 결정했다.

### 23-1. 다시 연 결정

22절의 다섯 결정 가운데 **1번의 사용자 행동만 확장한다.** 제품명, 첫 화면 제목, 제품 설명 이름,
9종 대 3종 정적 그림, 공개 URL과 ZIP 제출 결정은 유지한다.

V2의 사용자 행동은 다음 세 가지다.

1. 공급자가 준 성능 숫자와 가지고 있는 평가 근거를 입력한다.
2. 숫자의 운영 의미, 빠진 평가 조건, 수치와 조건의 충돌을 검토한다.
3. 공급자 질문에 답변 상태와 메모를 남기고 PoC 검토표를 복사하거나 인쇄한다.

### 23-2. 제품 결과물

질문 목록만 남기지 않고 한 번의 검토에서 다음을 포함한 **PoC 미팅용 검토표**를 만든다.

- 받은 주장과 혼동행렬에서 계산한 값
- 입력한 평가 조건과 확인되지 않은 조건
- 주장 지표와 혼동행렬 계산값의 불일치
- 서로 모순되는 평가 조건
- 공급자 질문, 답변 상태, 답변 메모
- 논문 근거와 이 앱이 하지 않는 판정

질문 상태는 `아직 묻지 않음 / 답변 받음 / 자료 요청 / 추가 확인` 네 가지다. 메모와 상태는 기존
입력처럼 컴포넌트 메모리에만 두며 새로 고치면 사라진다. 전체 검토표 복사와 브라우저 인쇄는 명시적
사용자 동작으로만 실행한다.

### 23-3. 새 판독

- **R11 — 주장 지표와 혼동행렬 불일치:** 같은 화면에 적은 Accuracy, Macro F1, 공격 Recall, FPR이
  혼동행렬 계산값과 화면의 소수 넷째 자리에서 다르면 `확인 필요`로 두고 같은 시험 결과인지 묻는다.
- **R12 — 평가 조건 모순:** `학습에 없던 공격을 따로 시험`했다고 답하면서 미관측 공격 포함 여부를
  `아니오`라고 답하면 `확인 필요`로 두고 두 답 가운데 어느 것이 맞는지 묻는다.
- **R13 — 다른 분할 방식:** 분할 방식이 `다른 방식`이면 구체적인 분할 기준과 공격 유형 구성을 묻는다.

어느 규칙도 모델 성능을 합격·불합격으로 판정하지 않는다.

### 23-4. 결과 화면 우선순위

모바일 결과 순서는 `숫자 뒤집기 → 평가 근거 지도 → 판독 → 질문과 답변 → PoC 검토표 → 논문 분할
그림`으로 둔다. 논문 분할 그림은 유지하되 사용자의 다음 행동인 질문과 검토표보다 앞에서 긴 스크롤을
만들지 않는다.

### 23-5. V2에서도 만들지 않는 것

- 서버 저장, 계정, 공유 링크
- 외부 AI API와 자동 판정
- PCAP·CSV 업로드와 모델 추론
- 업계 일반 임계값과 신뢰 점수

## 24. 대표 앱 V3 — 회차별 로컬 PoC 사례 작업대

> 승인일: 2026-09-22
> 목표: 한 번의 질문 생성을 넘어, 공급자에게 받은 자료의 출처와 회차를 남기고 판독 변화를 비교한다.

### 24-1. 다시 여는 결정

- 22절 1번의 사용자 행동을 한 번 더 확장한다. 최초 입력 → 질문 → 받은 자료 추가 → 재검토를 한 사례 안에서 반복한다.
- 3-5절과 23-2절의 `새로 고치면 사라진다`는 자동 저장에 대해서는 유지한다. 다만 사용자가 명시적으로 ExplainSOC 사례 JSON을 내려받고 다시 여는 것을 허용한다.
- 23-5절의 파일 업로드 금지는 PCAP·CSV·모델 입력에 대해 유지한다. 이 앱이 만든 버전 표시 JSON 한 종류만 예외다.
- 제품명, 첫 화면 제목, `성능표에 없는 질문`, 9종 대 3종 그림, 공개 URL과 ZIP은 유지한다.

### 24-2. V3의 사용자 행동

1. 최초 성능 주장과 평가 조건을 검토해 1회차를 만든다.
2. 공급자에게 받은 자료를 새 회차로 추가하고, 출처와 같은 시험 결과인지를 적는다.
3. `해결됨 / 남음 / 새로 생김`을 비교하고 자료 요청서와 PoC 검토표를 내보낸다.
4. 필요하면 사례 JSON을 로컬 파일로 저장해 다음 회의에서 다시 연다.

### 24-3. 회차와 출처

- 회차는 최초 입력의 불변 스냅샷이다. 이전 회차를 덮어쓰지 않는다.
- 각 회차는 `이름, 출처 종류, 출처 메모, 같은 시험 여부, 검증된 입력, 질문 상태·메모`를 가진다.
- 출처 종류는 `최초 제안서 / 공급자 답변 / 추가 시험 / 기타`다.
- `같은 시험`은 `예 / 아니오 / 모름`이다. `예`면 이전 값과 합쳐 재검토하고, `아니오`면 별도 시험으로 본다. `모름`이면 변화를 미리 보기 위해 임시로 겹쳐 계산하되, R14를 남겨 확인된 병합으로 표시하지 않는다.
- 회차 비교는 규칙 ID의 집합 차이로 계산한다. 자동 점수나 품질 판정을 만들지 않는다.

### 24-4. R14 — 받은 자료의 시험 출처

최초 입력 뒤의 회차에서 성능 지표나 혼동행렬을 받았지만 같은 시험 결과인지 `모름`이면 `확인 필요`로 둔다.

- 질문: `이번에 받은 지표와 혼동행렬은 기존 성능 주장과 같은 시험 결과입니까?`
- 값이 일치해도 출처를 알 수 없으면 질문을 남긴다.
- `아니오`면 모순으로 판정하지 않고 별도 시험 회차로 표시한다.

### 24-5. 로컬 사례 파일

- JSON 최상위에 `kind: "explainsoc-case"`, `schemaVersion: 1`을 둔다.
- 파일 크기는 1 MiB 이하만 받는다.
- 예상한 키와 자료형을 엄격히 검증한다. 문자열은 길이를 제한하고 HTML로 해석하지 않는다.
- URL, 쿠키, `localStorage`, `sessionStorage`, 외부 요청으로 자동 저장하지 않는다.
- 내려받기와 다시 열기는 명시적 사용자 동작으로만 실행한다.
- 파일에 입력 숫자와 메모가 포함된다는 경고를 내려받기 버튼 앞에 보인다.

### 24-6. 자료 요청서와 인쇄

- 질문마다 `요청할 자료`를 규칙과 함께 관리한다.
- 최종 출력은 받은 주장, 회차 요약, 판독 변화, 남은 질문, 요청할 자료, 답변 메모, 논문 근거를 포함한다.
- A4 인쇄는 첫 페이지에 요약과 남은 질문을 두고, 메모와 근거는 다음 페이지로 자연스럽게 넘어간다. 한 장에 맞추기 위해 글자를 작게 만들지 않는다.

### 24-7. 결과 화면과 접근성

- 작업대 상단에 `판독 / 질문·답변 / 회차 비교 / 최종 검토표`로 가는 같은 페이지 바로 가기를 둔다.
- 용어 풀이는 호버에만 의존하지 않고 키보드와 터치로 열 수 있는 한국어 설명으로 둔다.
- 작업 내비게이션은 본문을 가리는 고정 하단 바가 아니라 상단의 일반 링크다.

### 24-8. V3에서 만들지 않는 것

- 여러 공급자의 순위·점수 비교
- 안전·위험 신호등과 업계 기본 임계값
- 외부 LLM·모델 추론·PCAP·CSV

## 25. V3 독립 리뷰 반영 설계 — 비교의 의미와 기록 보존

> 설계일: 2026-09-22
> 상태: 구현·배포·재현 검증 완료
> 근거: `planning/CLAUDE-V3-REVIEW.md`의 R1~R5 코드 사실 확인

### 25-1. 범위와 원칙

이 변경은 새 제품 기능을 추가하는 V4가 아니다. 24절에서 승인한 회차형 작업대가 실제 업무에서
잘못 읽히거나 기록을 잃지 않도록 의미·산출물·입력 안내를 바로잡는 V3 완성 작업이다.

- 22절의 다섯 결정은 바꾸지 않는다.
- 24절의 JSON 형식 버전 1과 회차 원자료 구조를 유지한다.
- 이전 회차는 계속 불변 스냅샷으로 둔다.
- 자동 점수, 합격 판정, 서버 저장을 만들지 않는다.
- 화면, 복사한 검토표, 인쇄 결과가 같은 비교 의미를 사용한다.

### 25-2. 같은 시험 여부가 비교 방식을 결정한다 — R1

회차 비교 결과를 단순 `ReviewDiff` 하나가 아니라 다음 세 종류로 구분한다.

| 같은 시험 여부 | 비교 종류 | 화면과 산출물 |
|---|---|---|
| 예 | `confirmed` | `해결됨 / 남음 / 새로 생김`을 확정 비교로 표시한다 |
| 모름 | `provisional` | 같은 세 묶음을 `시험 출처 확인 전 임시 비교`로 표시하고 R14를 남긴다 |
| 아니오 | `separate` | 집합 차이를 해결로 해석하지 않는다. `이전 시험 판독 / 이번 별도 시험 판독`을 나란히 표시한다 |

`아니오`에서도 새 회차 입력만으로 현재 판독을 만드는 기존 계산은 유지한다. 달라지는 것은 서로 다른
시험 사이의 규칙 소멸을 `해결됨`이라고 부르지 않는 것이다. 화면과 검토표 어디에도 별도 시험을
`해결됨 / 남음 / 새로 생김`으로 표현하지 않는다.

권장 도메인 구조는 판별 가능한 합집합이다.

```text
RoundComparison =
  confirmed(diff)
  | provisional(diff)
  | separate(previousFindings, currentFindings)
```

컴포넌트가 `sameTrial`을 다시 해석하지 않고 도메인에서 만든 이 결과만 그리게 한다.

### 25-3. 회차별 답변 상태와 메모를 보존해 보여 준다 — R2

JSON에는 이미 회차별 `responses`가 있으므로 형식을 바꾸지 않는다. 다음 회차를 시작할 때 직전 회차의
응답을 복사해 현재 회차의 편집 초깃값으로 사용한다. 이전 회차 객체는 수정하지 않는다.

- 현재도 남아 있는 같은 질문: 직전 상태와 메모를 기본값으로 보여 준다.
- 새로 생긴 질문: `아직 묻지 않음`, 빈 메모로 시작한다.
- 사라진 질문: 현재 질문 목록에는 없지만 이전 회차 기록에는 그대로 남긴다.
- 사용자가 현재 회차에서 바꾼 상태와 메모는 현재 회차에만 저장한다.

검토표의 각 회차 아래에는 다음 중 하나라도 해당하는 응답만 출력한다.

- 상태가 `아직 묻지 않음`이 아님
- 메모가 비어 있지 않음

각 줄에는 질문, 당시 상태, 메모를 함께 둔다. 마지막의 `남은 공급자 질문과 답변`은 현재 회차의
업무 목록으로 유지한다. 따라서 회차 기록은 이력이고 마지막 목록은 다음 행동이다.

### 25-4. 후속 회차 입력에서 상속과 변경을 구분한다 — R3

후속 회차 1·2단계 맨 위에 다음 안내를 둔다.

> N회차 · 이번에 새로 받은 자료만 적으세요. 비운 칸은 이전 회차 값을 이어 씁니다.

입력 칸에는 이전 유효 값을 읽기 전용 보조 정보로 보여 주되 폼에 미리 채우지 않는다. 미리 채우면
회차 원자료에 이전 값이 다시 저장되어 불변 스냅샷과 파생 계산의 경계가 흐려지기 때문이다.

- 숫자·혼동행렬: `이전 회차 값`을 입력 아래에 표시한다.
- 분할·미관측 공격·중복 제거: 각 질문 아래에 `이전 값: …`을 표시한다.
- 아무것도 선택하지 않음: 이전 값을 유지한다.
- `모름`을 명시적으로 선택: `이전의 예/아니오를 모름으로 바꿉니다`라고 바로 알린다.

보조 문구는 입력과 `aria-describedby`로 연결한다. 최초 회차에는 이 안내와 이전 값이 나오지 않는다.

### 25-5. 출력물의 규칙과 근거를 사람 말로 쓴다 — R4

규칙과 근거 ID는 추적 가능성을 위해 남기되 ID만 출력하지 않는다.

- 판독: `R04 · 공격 Recall 없는 오탐률`
- 논문 근거: `P03 · 원고 V-2 · 미관측 공격 결과`

화면, 공급자 자료 요청서, 검토표가 같은 포맷 함수를 사용한다. `해결됨`에 들어가 현재 판독 목록에서
사라진 규칙도 제목을 함께 쓰므로 종이만 받아도 뜻을 알 수 있어야 한다.

요청서의 각 질문은 계속 `질문 / 요청할 자료 / 이유 / 근거` 순서로 두고, 끝에는 실제로 사용한 근거만
중복 없이 모은 `근거 목록`을 둔다. 원문 전체 인용은 넣지 않고 ID·원고 절·짧은 제목만 쓴다.

### 25-6. 같은 시험 선택 칸과 키보드 포커스 — R5·L3

`기존 주장과 같은 시험입니까?` 칸은 데스크톱 2열 그리드에서도 전체 행을 사용한다. 선택지 문구는
`예 — 같은 시험으로 합쳐 보기 / 아니오 — 별도 시험 / 모름 — 임시 비교 후 출처 확인`을 줄이지 않는다.
이는 단순 레이아웃 문제가 아니라 R14와 비교 방식의 입력이므로 설명을 보존한다.

같은 UI 수정 묶음에서 파일 열기의 포커스 테두리도 실제로 보이는 label 전체에 표시한다. 키보드로
탭 이동했을 때 `검토 파일 열기` 버튼의 경계가 보여야 한다.

### 25-7. 사례 파일의 모호한 값 거부 — L2

앱이 생성하는 파일의 규칙과 가져오기 검증을 일치시킨다.

- 1회차의 `sameTrial`만 `null`을 허용한다.
- 2회차 이후는 `yes / no / unknown` 중 하나여야 한다.
- 회차 이름과 사례 이름은 앞뒤 공백을 뺀 뒤 한 글자 이상이어야 한다.
- 기존 정상 V3 파일의 `schemaVersion: 1`은 유지한다.

이는 파일 형식 확장이 아니라 이미 화면과 저장 코드가 만드는 값만 받아들이도록 검증을 좁히는 것이다.

### 25-8. 수용 시나리오

1. 논문 예시의 R04에서 다음 회차에 공격 Recall 0.0007을 넣고 `모름`이면 임시 비교, R14, 임시
   `해결됨 R04`가 함께 보인다.
2. 같은 입력에서 `예`를 고르면 확정 비교가 되고 R14가 사라진다.
3. 같은 입력에서 `아니오`를 고르면 `해결됨`이라는 말이 사라지고 이전 시험의 R04와 이번 별도 시험의
   판독이 나란히 보인다. 검토표도 같다.
4. 1회차에 `자료 요청`과 메모를 남긴 뒤 2회차로 가면 계속 남은 질문에 그 값이 기본으로 보인다.
   값을 바꿔도 1회차 JSON은 바뀌지 않는다.
5. 2회차 1·2단계에는 회차 안내와 이전 값이 보인다. 빈 칸은 상속되고 명시적 `모름`은 변경 경고 뒤
   이전 값을 덮어쓴다.
6. 복사한 자료 요청서와 검토표만 읽어도 R·P 코드의 뜻과 원고 위치를 알 수 있다.
7. 560px 이상 화면에서 같은 시험 선택 문구가 잘리지 않고, 375px에서는 가로 넘침이 없다.
8. 키보드만으로 사례 파일 열기까지 이동했을 때 보이는 포커스가 있다.
9. 후속 회차의 `sameTrial: null`과 공백뿐인 이름을 가진 손수 수정 JSON은 오류로 거부한다.

### 25-9. 테스트와 완료 순서

1. 도메인 테스트: 세 비교 종류, 응답 이어받기, 사람이 읽는 규칙·근거 포맷, JSON 검증 경계를 먼저 쓴다.
2. 컴포넌트 테스트: 별도 시험 화면, 이전 값 안내, 회차별 응답 이력, 선택 칸과 파일 열기 포커스를 검증한다.
3. 브라우저 테스트: 25-8의 `모름 → 예 → 아니오`, 메모 보존, JSON 왕복, 375px·데스크톱 흐름을 검증한다.
4. 기존 V1·V2 핵심 흐름, 안전 검사, 접근성 검사를 모두 다시 돌린다.
5. V3 증거 스크린샷을 현재 코드로 다시 찍어 L1을 닫는다.
6. 구현 커밋 배포가 성공하면 공개 자산 해시와 공개 URL 브라우저 검사를 확인한다.
7. 새 구현 커밋으로 ZIP을 두 번 만들고 저장소 밖 빈 폴더에서 전체 검증한다.
8. `card-5`, 인계 문서, 12번 대표작의 테스트 수와 V3 설명을 마지막 실제 값으로 다시 갱신한다.

완료 조건은 테스트 통과만이 아니다. `아니오`를 고른 사람이 이전 문제가 해결됐다고 오해하지 않고,
최종 검토표만 받은 사람이 어느 회차에 무엇을 요청하고 답받았는지 재구성할 수 있어야 한다.

## 26. 대표 앱 V4 — 성능 주장 수사 보드

> 승인일: 2026-09-22
> 목표: 논리적으로 완성된 V3를 처음 10초에 기억되고 실제 회의에서 꺼내 쓰고 싶은 대표 제품으로 재구성한다.

### 26-1. 제품 서사

V4의 대표 경험은 세 장면이다.

1. **주장 해부:** `99.88%`라는 단일 숫자가 시험 방식에 따라 `0.9979 / 0.3871`로 갈라지고,
   공격 220,788건 중 탐지 160건이라는 운영 의미로 바뀐다.
2. **시험 분기:** 공급자 답변이 같은 시험인지에 따라 확정 병합, 임시 연결, 별도 시험 분기로 보인다.
3. **회의 문서:** 남은 질문과 받을 자료가 앞장에 있는 Decision Dossier를 복사하거나 PDF로 가져간다.

### 26-2. 정보 구조

- 첫 화면은 설명문보다 `성능 주장 → 시험 조건 → 운영 의미`의 변화를 먼저 보여 준다.
- 결과 화면 맨 위에는 회차·출처·시험 분기를 둔다. V3의 핵심을 페이지 아래에 숨기지 않는다.
- 데스크톱 작업대는 `주장과 근거 / 판독 / 다음 행동` 세 열이다.
- 모바일은 같은 순서를 세로 이야기로 유지한다. 축소된 데스크톱 보드를 만들지 않는다.
- 긴 논문 분할 그림과 개발자용 세부 근거는 핵심 행동 뒤에 둔다.

### 26-3. 근거 지도

점수나 신호등 대신 여섯 근거의 상태를 보여 준다.

`성능 지표 / 혼동행렬 / 분할 정의 / 미관측 공격 / 중복 감사 / 시험 연결`

각 항목은 `받음 / 확인 필요 / 해당 없음` 가운데 하나만 가진다. 합계와 완성도 점수는 만들지 않는다.

### 26-4. Decision Dossier

검토표 앞장에는 `회차, 현재 판독 수, 다음 질문 수, 비교 상태`를 큰 숫자와 문장으로 보여 준다.
원문 텍스트는 추적 가능한 상세 기록으로 유지하고, 앞장은 화면과 인쇄에서 같은 의미를 사용한다.

### 26-5. 시각 언어

- 미드나이트 네이비 배경 위에 아이보리 문서를 놓는다.
- 코발트는 받은 근거, 앰버는 확인 필요, 자주는 별도 시험 분기, 녹색은 같은 시험에서 해결된 항목이다.
- 보안 제품을 흉내 낸 네온·레이더·신호등은 쓰지 않는다.
- 큰 숫자와 짧은 문장을 우선하고 메타데이터만 고정폭 글꼴을 쓴다.
- 모션은 주장 해부와 시험 분기에만 쓰며 `prefers-reduced-motion`에서는 즉시 전환한다.

### 26-6. 유지하는 경계

- R01~R14, 회차 JSON, 질문 상태·메모, CSP와 안전 검사는 그대로 사용한다.
- 자동 판정, 공급자 순위, 임의 완성도 점수, 서버·계정·자동 저장은 추가하지 않는다.
- 22절의 제목·제품명·정적 분할 그림·공개 URL과 ZIP 결정을 바꾸지 않는다.

### 26-7. V4 완료 기준

- 첫 화면만 본 사람이 `성능 숫자는 시험 조건과 함께 봐야 한다`고 말할 수 있다.
- 결과 화면 첫 뷰포트에서 현재 회차, 같은 시험 여부, 주요 판독, 다음 질문을 찾을 수 있다.
- 별도 시험 선택이 타임라인과 판독 보드 모두에서 분기로 보인다.
- 검토표 원문을 펼치지 않아도 다음 회의에서 받을 자료의 개수를 알 수 있다.
- 375px 가로 넘침, 키보드, WCAG 2.2 AA, 인쇄, 기존 V1~V3 회귀 검사를 통과한다.

## 27. 대표 앱 V5 — 결과를 먼저 읽는 Decision Brief

> 결정일: 2026-09-22
> 목표: V4의 강한 첫 화면을 결과에서도 유지하고, 긴 기능 목록보다 현재 판단과 다음 질문을 먼저 읽게 한다.

### 27-1. V4에서 확인한 문제

- 논문 예시를 시작하면 핵심 판독보다 회차 이름·출처·메모 입력 폼이 먼저 나왔다.
- 3열 보드의 콘텐츠 높이가 달라 긴 빈 컬럼이 생겼고, 하나의 완성된 제품보다 카드가 쌓인 대시보드처럼 보였다.
- 모바일에서 근거·판독·다음 행동·회차 기록이 모두 세로로 이어져 전체 캡처 높이가 약 8,856px였다.
- 상단 바로가기는 결과 구조를 설명하지 못했고 스크롤을 시작하면 현재 위치를 잃기 쉬웠다.

### 27-2. 결과 진입 순서

결과 화면의 읽기 순서를 다음으로 고정한다.

1. **Decision Brief:** 현재 회차, 확인 필요 수, 해석 주의 수, 다음 질문 수와 첫 질문
2. **주장과 근거:** 숫자 뒤집기를 맨 앞에 두고 근거 지도와 평가 조건을 잇는다
3. **판독:** 숫자가 말하는 것과 말하지 않는 것을 규칙별로 읽는다
4. **다음 행동:** 질문 상태·메모, 자료 요청서, Decision Dossier
5. **회차 기록:** 첫 검토에서는 접어 두고 공급자 답변을 연결할 때 연다

Decision Brief는 점수나 위험 등급이 아니다. `판정 아님 · 근거 확인`을 항상 표시하고, 숫자의
좋고 나쁨 대신 현재 입력에서 먼저 확인할 일을 한 문장으로 쓴다.

### 27-3. 데스크톱 편집형 보드

- 3열을 같은 높이의 색상 컨테이너로 만들지 않는다. 각 열은 독립된 문서 카드 묶음이며 내용 높이만큼만 차지한다.
- 열 머리글에는 01·02·03 번호와 다른 상단 색을 써 읽는 순서를 보인다.
- 배경의 옅은 격자는 조사 보드의 맥락만 주고, 정보 카드보다 강해지지 않는다.
- 회차 편집기를 보드 아래로 옮겨 첫 뷰포트에서 현재 판단과 첫 질문을 찾게 한다.
- REVIEW MAP은 화면 위에 붙어 있으며 근거·판독·행동·회차·산출물로 바로 이동한다.

### 27-4. 모바일 작업 탭

375px에서는 데스크톱 3열을 길게 쌓지 않는다. `01 주장·근거 / 02 판독 / 03 다음 행동` 가운데
하나만 보여 주고 상단 작업 탭으로 전환한다. 현재 장은 `aria-pressed`로 전달하며 키보드와 터치로
같이 사용할 수 있어야 한다.

- 첫 진입은 주장·근거다.
- Decision Brief의 첫 질문 버튼은 바로 다음 행동 장을 연다.
- 회차 기록은 별도 서랍으로 접고, 후속 회차 파일을 열었을 때는 펼친 상태로 시작한다.
- 모바일 전체 문서 길이를 줄이되 모든 기능과 근거는 삭제하지 않는다.

### 27-5. 모션과 경계

- 첫 화면의 두 성능 막대만 짧게 펼쳐지는 모션을 더한다.
- `prefers-reduced-motion`에서는 즉시 최종 상태가 된다.
- R01~R14, P01~P10, 계산식, 질문 문구, JSON 형식, 보안 경계는 바꾸지 않는다.
- 자동 판정·신뢰 점수·새 네트워크 요청·사용자 추적은 추가하지 않는다.

### 27-6. 완료 기준

- 논문 예시 진입 직후 현재 해석 주의 수와 첫 공급자 질문을 볼 수 있다.
- 데스크톱에서 3열의 큰 빈 컬럼이 사라지고 회차 편집기는 보드 뒤에 나온다.
- 모바일에서 세 작업 장이 한 번에 하나만 보이고 375px 가로 넘침이 없다.
- 첫 질문 버튼과 작업 탭이 올바른 장을 열며 키보드로도 동작한다.
- Vitest 92개, Playwright 기능·품질 검사 26개, 증거 캡처 9개, 안전 검사 11개를 통과한다.
- 배포 뒤 공개 주소에서도 같은 브라우저 검사를 통과하고 V5 커밋 기준 ZIP을 새로 만든다.

## 28. V6 — 비전공자 첫 10초 명료화

> 결정일: 2026-09-22
> 근거: 실제 비전공자 한 명이 첫 화면을 보고도 무엇을 하는 사이트인지 이해하지 못했다.

### 28-1. 문제

V5 첫 화면은 `평가 조건`, `공급자`, `Claim Autopsy`처럼 대상 업무를 아는 사람에게는 정확하지만,
비전공자에게는 언제 왜 쓰는지 설명하지 못했다. 시각 완성도와 기능 수가 높아도 첫 10초에 목적을
말하지 못하면 포트폴리오 방문자가 결과 화면까지 들어가지 않는다.

### 28-2. 바꾸는 것

- 제목에 `보안 AI`를 직접 넣어 분야를 먼저 밝힌다.
- 도움 문장은 `광고 숫자를 확인하고 판매 업체에 물어볼 질문을 만드는 도구`라는 쉬운 말로 쓴다.
- `회사에서 AI 제품 자료를 받았지만 무엇을 시험했는지 모를 때`라는 사용 상황을 한 줄로 보인다.
- 세 단계는 `숫자 입력 → 모르는 시험 조건 답변 → 업체 질문 완성`으로 쓴다.
- 기존 수치, 논문 근거, 판독 규칙, 결과 구조와 보안 경계는 바꾸지 않는다.

### 28-3. 완료 기준

- 첫 화면에 대상 분야, 입력, 결과, 사용 상황이 전문 용어 없이 보인다.
- 컴포넌트 테스트가 쉬운 설명과 사용 상황 문장을 고정한다.
- 375px 가로 넘침과 WCAG 2.2 AA 검사를 계속 통과한다.
- 수정 뒤 기존 참가자가 아닌 새로운 처음 보는 사람에게 다시 보여 준다.

## 29. 대표 앱 V7 — 한 장씩 읽는 결과와 크기 그림

> 승인일: 2026-09-23
> 근거: 앱을 처음 보는 두 사람의 관찰(`evidence/card-5.md` — 두 번째 관찰). 버튼을 누른 뒤 나오는 화면이
> 너무 밀집해 읽기 힘들고, 그림이 있으면 좋겠다는 의견을 받았다.

### 29-1. 확인한 사실

V6 결과 화면은 1280px에서 5.2화면 길이에 패널 16개를 세 열로 동시에 펼쳤다. 첫 화면은 크고 여백이 넓은데
결과부터 글상자 밀도가 갑자기 올라간다. 회차·판독·질문·검토표가 같은 무게로 한꺼번에 보인다.

### 29-2. 바꾸는 것

- 결과는 `주장과 근거 → 판독 → 다음 행동` 세 장을 **한 번에 한 장만** 보인다. 모바일에만 있던 전환을
  모든 화면 폭으로 옮기고, 한 열을 넓게 쓴다.
- 장 아래에 `이전 / 다음` 단추와 `N / 3` 위치를 둔다. 위쪽 REVIEW MAP을 찾지 못해도 순서가 이어진다.
- 받은 혼동행렬을 `공격 N건 가운데 탐지 M건`, `정상 N건 가운데 오탐 M건`의 **실제 비율 막대**로 그린다.
  축을 자르거나 최소 너비를 주지 않는다. 눈에 보이지 않는 값은 눈금과 글로 알린다.
- 잘못 적은 칸 수는 판독 장을 열기 전에 브리핑에서 먼저 알린다.
- 인쇄는 지금 보고 있는 장과 무관하게 검토표 전체를 낸다.

### 29-3. 하지 않는 것

- 캐릭터·삽화로 도구의 성격을 바꾸지 않는다. 그림은 받은 숫자를 그리는 데만 쓴다.
- 비율을 과장해 보이게 최소 길이를 주거나 축을 자르지 않는다.
- 점수·등급·합격선을 만들지 않는다. 그림에도 `합격선이 아니다`를 적는다.
- 기능, 판독 규칙 R01~R14, 회차 JSON, 보안 경계는 그대로 둔다.

### 29-4. 완료 기준

## 30. V8 — 밝은 문서형 화면과 두 가지 입력 방식

> 근거: V7을 한 바퀴 돌려 본 뒤의 사용자 판단과 지금까지의 관찰(`evidence/card-5.md`)에서 반복된
> "한꺼번에 너무 많이 보인다". 작업 기록은 `planning/HANDOFF-2026-09-23-UI.md`에 있다.

### 30-1. 확인한 문제

1. 길 안내가 세 겹이었다: 위 단계 1·2·3, 결과 안의 `REVIEW MAP 01~05`, 아래 `1/3` 장 이동.

### 30-2. 바꾸는 것

- 첫 화면을 포함한 모든 화면을 **밝고 깔끔한 문서형**으로 바꾼다. 흰 문서 카드, 연한 회색 바탕
  (`--paper #f4f5f7`), 강조색 하나(`--accent #2450c7`)만 쓴다.
- 영어 라벨을 한국어로 바꾼다. 단계 이름은 `PoC 검토표` → `검토 결과`, 결과 제목은 `3. 검토 결과`,
  결과 요약은 `검토 요약`, 결과 목차는 번호 붙은 밑줄 탭(①주장과 근거 ②판독 ③다음 행동)이다.
  회의에 가져가는 결과물 이름 "PoC 성능 주장 검토표"는 그대로 둔다.
- 입력은 두 방식을 둔다.
  - **처음 입력은 한 화면씩**(`GuidedInput`): 질문 6개를 하나씩, `질문 N / 6` 진행 막대, 큰 선택지 카드와
    한 줄 설명, 늘 보이는 "왜 묻나요?" 상자. 답하지 않은 질문은 `건너뛰고 다음`으로 넘기며 `모름`과 같게 읽힌다.
  - **고칠 때와 2회차 이후는 한 페이지**(`OnePageForm`): A 받은 숫자, B 평가 조건 두 구역과 붙어 있는
    `N / 6 답함 · 결과 보기`. 한 화면씩에서 `질문 전체 한 번에 보기`로도 옮길 수 있고, 입력값은 유지된다.
  - 이유(추론): 대상은 주니어 담당자이고, 관찰된 실패 원인이 "한꺼번에 너무 많이 보임"이었다. 처음에는
    질문 하나와 설명 하나만 보여야 `모름`을 부담 없이 고른다. 이미 읽은 사람은 한 페이지에서 바뀐 것만 고치는 편이 빠르다.
    이 추론은 새로운 처음 보는 사람 재시험(BRB-C11)에서 확인해야 한다.
- 결과 1장의 두 근거 패널을 **근거 확인표 하나로 합친다.** 6칸(성능 지표·혼동행렬·분할 정의·미관측 공격·
  중복 감사·시험 연결)을 남기고, 평가 근거 지도에만 있던 세 가지를 옮긴다: `평가 조건 확인` 단추,
  분할과 미관측 공격 답이 어긋날 때의 R12 안내(두 칸을 빨간 테두리로 표시), "모름은 실패가 아니다" 문장.
- 요약·목차·장·회차 기록·단추를 960px 한 열로 맞춘다.

### 30-3. 하지 않는 것

- 판독 규칙 R01~R14, 수치, 회차 JSON, 보안 경계는 바꾸지 않는다. 합친 근거 확인표도 같은 입력에서 같은 내용을 보인다.

## 31. V9 — 받은 소개서를 그대로 읽고, 논문 뒤쪽 절반을 직접 바꿔 본다

> 승인일: 2026-09-24 (사용자가 "V9로 해도 돼, 급한 것도 아니고"라고 정해 `v9-brochure` 브랜치에서 진행했다)
> 근거: `evidence/card-5.md` 세 번째~다섯 번째 관찰, 동기들이 자기 논문으로 만든 앱을 본 뒤 "더 좋고 풍부한 앱이
> 되었으면 한다"는 사용자의 판단, 그리고 앱이 논문 원고 V-2의 두 분할 표만 쓰고 V-3~V-5를 쓰지 않던 사실.

### 31-1. 확인한 문제

1. 받은 자료는 보통 소개서 문장이다. 그런데 앱은 사용자가 숫자와 조건을 칸에 옮겨 적어야 시작했다.
2. 비전공 지인이 첫 화면에서 "이게 뭔데? 전문적인 것 같아 안 쓸 것 같다"고 했다(세 번째 관찰).
3. 결과를 보고 "좋은 건지 나쁜 건지 모르겠다, 그래서 뭐?"라고 했다(네 번째 관찰). 결과 첫머리에 결론이 없었다.
4. 논문의 모델 비교(V-2 표 3개 모델), 시드 반복(V-2), 분할별 SHAP 상위 특징(V-3), 설명 안정성(V-4),
   치환 민감도(V-5)가 앱에 없었다. 소개서에 자주 나오는 "설명 가능한 AI" 주장을 읽는 규칙도 없었다.
5. 사용자가 보여 줄 상대를 **전문가나 어느 정도 지식이 있는 사람**으로 보자고 정했다. 비전공자의 첫 10초는
   지키되, 안쪽 화면은 보안 담당자가 논문을 직접 확인할 수 있을 만큼 풍부해야 한다.

### 31-2. 바꾸는 것

- **첫 화면**: 시험 공부 비유로 다시 쓴다. 제목 "보안 AI의 99점, 처음 보는 공격에서도 99점일까요?", 큰 단추는
  `예시로 바로 보기` 하나, 그 아래 `내 자료로 해 보기` 줄에 `소개서 문장 붙여 넣기`·`숫자로 직접 입력`.
  오른쪽 그림 "같은 AI, 두 번의 시험"(99.8점 / 38.7점, Macro F1 ×100) 아래에 짙은 **논문 실험실 카드**를 둔다.
- **소개서 판독**(`BrochureReader`, `domain/brochure.ts`): 붙여 넣은 문장(최대 5,000자)에서 정해 둔 표현만
  규칙으로 찾는다 — 성능 숫자, 최고 성능 주장, 분할 방식, 학습에 없던 공격으로 따로 시험, 신종 공격 탐지 주장,
  중복 제거, 설명 가능한 AI 주장. 문장 위에 형광펜(공급자 주장)·밑줄(시험 조건)과 번호를 붙이고, 번호마다
  메모(읽은 값, 논문 근거, 이 표시로 생긴 질문)를 단다. 표시와 메모는 짝끼리 같이 밝아진다. 소개서에 없어
  질문이 된 조건은 따로 모은다. 소개서를 고쳐도 사용자가 직접 답한 조건은 지우지 않는다(`applyBrochure`).
  "신종 공격까지 탐지"는 능력 주장이지 시험 조건이 아니므로 조건 답으로 바꾸지 않는다. 예시 소개서는 **가상**이며
  논문 무작위 분할 숫자를 빌렸다고 화면에 적는다.
- **결론 카드**(`ConclusionCard`, `domain/conclusion.ts`): 결과 맨 위에 결론 · 왜? · 그래서?를 둔다.
  - 상태는 세 가지다. `믿기 전에 확인`(처음 보는 공격으로 시험한 근거 없음), `숫자 하나가 더 필요`(그렇게
    시험했지만 공격을 잡는 숫자 없음), `숫자로 직접 판단`(둘 다 있음).
  - 왜?는 시험 조건 한 줄과 받은 숫자 한 줄이다. 받은 숫자는 "100건으로 치면"으로 옮긴다.
  - 막대는 믿기 이를 때 논문의 두 시험(99.8점 / 38.7점)을, 공격 Recall을 알 때 입력한 숫자를 그린다.
  - 그래서?는 짙은 띠에 질문 수와 `업체에 물을 질문 보기` 단추를 둔다.
  - 입력에 맞는 실험실 카드(최고 성능·무작위 분할 → 실험 1, 설명 주장 → 실험 4)를 붙인다.
- **논문 실험실**(`PaperLab`): 짙은 첫머리와 실험 목차 네 칸, 실험마다 번호 배지를 둔다.
  1. 1위는 시험이 정합니다(V-2): 시험 두 가지 × 기준 세 가지(Macro F1·공격 Recall·FPR)로 세 모델 순위를 바꿔 본다.
  2. 운이 아니었습니다(V-2): XGBoost 시드 42·314·2026의 여섯 자리 값.
  3. 설명도 시험을 탑니다(V-3): 두 분할의 SHAP 상위 5개 특징과 순위 이동.
  4. 설명이 안정적이라고 잘 잡는 것은 아닙니다(V-4·V-5): Top-5 Jaccard와 공격 Recall, 상위 특징을 0~5개
     지웠을 때 예측이 바뀐 비율.
  수치는 `paperEvidence.ts`의 `MODEL_TABLE`·`SEED_TABLE`·`SHAP_TOP5`·`EXPLANATION_STABILITY`·`PERMUTATION`에
  있고 근거 P11~P14로 원고와 이어진다. 치환의 Top-1·2·4 단계는 원고 표에 없어 연구 저장소의
  `prepaper-shap-perturbation.json`에서 가져왔다. 모두 연구 저장소 보고서 JSON과 대조했다.
- **판독 규칙 R15** "설명 가능한 AI라는 주장"(확인 필요, 근거 P14·P08): 질문은 "보여 준 설명은 어떤 시험
  자료로 학습한 모델의 것이고, 같은 시험에서 공격 Recall은 얼마입니까?". 입력에 선택 항목 `claimedExplanation`을
  더했다. 이 값은 소개서 판독에서만 채워지고(한 화면씩·한 페이지 입력의 질문 6개는 그대로), 이 항목이 없는 예전 사례 JSON도 그대로 열린다.
- 판독 메모와 결론 카드에서 실험실의 그 실험으로 바로 가고, 돌아가기는 온 곳(소개서 판독·검토 결과·첫 화면)으로 간다.

### 31-3. 하지 않는 것

- AI API를 부르지 않는다. 소개서 판독은 규칙이며, 놓친 표현은 `빠진 조건 직접 답하기`와 `입력 수정`으로 고친다.
- 붙여 넣은 문장은 브라우저 메모리에만 둔다. URL, 저장소, 쿠키, 사례 JSON에 넣지 않는다(사례 JSON에는 문장에서 읽은 입력값만 들어간다).
- 결론 카드는 제품을 좋다·나쁘다로 판정하지 않는다. 점수·등급·합격선·기준선을 만들지 않는다.
- 새 수치를 만들지 않는다. 실험실은 논문과 연구 보고서의 숫자를 옮길 뿐이고, 치환 결과를 인과 효과로 읽지 않는다.
- R01~R14의 조건·문구, 논문 수치, 보안 경계(CSP `connect-src 'none'`)는 바꾸지 않는다.
- 첫 화면을 전문 용어로 되돌리는 안(전문가용 첫 화면)은 제안만 했고, 사용자가 정하지 않아 넣지 않았다.

### 31-4. 완료 기준

- 첫 화면 → 소개서 붙여 넣기 → 판독 → 결과(결론 카드) → 실험 1·4 → 돌아가기 흐름과, 첫 화면 → 실험실 →
  첫 화면 흐름이 데스크톱과 390px에서 가로 넘침·페이지 오류 없이 끝난다.
- 소개서 판독과 실험실이 axe WCAG 2.2 AA와 금지 표현 검사를 통과한다.
- 예시 소개서에서 표시 6곳(정확도·오탐률·무작위·신종 공격·업계 최고·SHAP)과 질문 7개(R01·R03·R04·R05·R07·R09·R15)가 나온다.

- 수정 뒤 앱의 대상에 가까운 처음 보는 사람(예: 학원 동기)에게 **V9**를 다시 보여 준다.
