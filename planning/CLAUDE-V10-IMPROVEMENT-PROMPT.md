# ExplainSOC V10 개선 요청 — 완성도 10점에 가깝게 끌어올리기

## 역할

당신은 현재 `t13-explainsoc` 프로젝트를 이어서 작업하는 구현 담당 Claude다.

이 프로젝트는 T13 과제 **“10번 논문의 결과를 실제로 쓰는 애플리케이션”**이며, 현재 공개 주소는 다음과 같다.

- https://myeongjundev.github.io/explainsoc/

현재 V9는 기능적으로 상당히 완성되어 있고, 논문 결과를 실제 검토 도구로 바꾸는 데 성공했다. 이번 작업의 목적은 기능을 무작정 늘리는 것이 아니라, 아래 5개 항목을 **10점에 가까운 수준으로 끌어올리는 것**이다.

1. 처음 보는 사람의 이해도
2. UI / 정보 구조
3. 기능 완성도
4. 포트폴리오 가치
5. 네트워크·보안 직무 연결

단, 현재의 논문 근거·수치·판독 규칙·안전 경계·테스트·재현성을 훼손하면 안 된다.

# 0. 먼저 읽을 것

작업 전 반드시 아래 문서를 읽고 현재 상태와 의도를 파악한다.

1. `planning/T13-ASSIGNMENT.md`
2. `planning/DESIGN.md`
3. `planning/STATUS.md`
4. `evidence/card-5.md`
5. `README.md`
6. `TROUBLESHOOTING.md`

특히 `evidence/card-5.md`의 실제 사용자 관찰 기록을 중요하게 본다.

기존에 확인된 문제는 다음과 같다.

- 첫 방문자가 무엇을 하는 사이트인지 바로 이해하지 못한 적이 있다.
- 결과 화면이 너무 밀집되어 읽기 힘들다는 반응이 있었다.
- “결과가 나왔는데 그래서 뭐?”라는 반응이 있었다.
- 일반인은 “보안 AI 광고”라는 상황 자체를 경험해 본 적이 없을 수 있다.
- V9에서 시험 공부 비유, 결론 카드, 소개서 판독, 논문 실험실까지 개선했다.

이번 작업은 이 문제들을 다시 되풀이하지 않아야 한다.

# 1. 이번 개선의 핵심 원칙

## 원칙 A — 기능 추가보다 이해 순서를 먼저 고친다

새로운 기능을 추가하기 전에 사용자가 아래 순서대로 이해할 수 있어야 한다.

```text
이게 왜 필요한가
→ 이 앱이 무엇을 해 주는가
→ 내가 뭘 누르면 되는가
→ 결과가 무엇을 뜻하는가
→ 그래서 다음에 무엇을 해야 하는가
→ 논문 근거가 무엇인가
```

처음부터 모든 정보를 보여주지 않는다.

---

## 원칙 B — 첫 방문자는 보안 비전공자일 수 있다

실제 핵심 사용자는 보안 AI 제품이나 PoC 자료를 검토하는 사람이다.

하지만 포트폴리오를 처음 보는 사람은 다음일 수 있다.

- 채용 담당자
- 개발자
- 보안 비전공자
- 교수·멘토
- ALEPH 동기

따라서 첫 화면은 **보안 지식 없이도 10초 안에 의미가 전달**되어야 한다.

단, 앱 내부의 전문성까지 없애라는 뜻은 아니다.

첫 화면은 쉬워야 하고, 들어갈수록 전문적이어야 한다.

```text
입구: 누구나 이해
중간: 실무자 사용
깊은 영역: 논문·보안·ML 근거
```

이 3단 구조를 지향한다.

---

## 원칙 C — 점수 평가기가 아니라 “증거 확인 도구”라는 정체성을 유지한다

ExplainSOC는 AI 제품에 대해 좋다 / 나쁘다를 판정하는 앱이 아니다.

핵심은 다음이다.

> 높은 성능 숫자를 그대로 믿기 전에, 그 숫자가 어떤 시험에서 나온 결과인지 확인하고 공급자에게 필요한 질문을 만들게 하는 도구

따라서 다음 같은 표현은 피한다.

- 이 제품은 위험하다
- 이 제품은 나쁘다
- 이 AI는 사용할 수 없다
- 이 점수는 거짓이다

대신 다음 방향을 유지한다.

- 확인이 더 필요하다
- 시험 조건이 부족하다
- 같은 시험인지 확인해야 한다
- 공격 Recall을 함께 봐야 한다
- 공급자에게 이 질문을 해야 한다

# 2. 목표 1 — 처음 보는 사람의 이해도 10점에 가깝게

현재보다 더 명확하게 아래 3가지를 첫 화면에서 전달해야 한다.

## 2-1. 10초 안에 이해해야 하는 세 문장

사용자가 첫 화면만 보고 아래 질문에 답할 수 있어야 한다.

1. 이 앱은 누구를 돕는가?
2. 무엇을 해 주는가?
3. 첫 번째로 무엇을 누르면 되는가?

가능하면 첫 화면 핵심 문구를 다음 구조로 재검토한다.

```text
문제
“정확도 99%”만 보고 보안 AI를 믿어도 될까요?

도움
ExplainSOC는 그 숫자가 어떤 시험에서 나온 것인지 확인하고,
판매 업체에 물어볼 질문을 만들어 줍니다.

첫 행동
[예시로 1분 만에 보기]
```

문구를 그대로 쓰라는 뜻은 아니다.
현재 V9보다 더 쉬워지는 경우에만 바꾼다.

---

## 2-2. 실제 상황을 한 줄로 보여 준다

“보안 AI 광고”라는 표현만으로는 일반인이 상황을 떠올리지 못할 수 있다.

예를 들어 아래와 같은 실무 상황을 아주 짧게 전달하는 방법을 검토한다.

> 회사에서 보안 AI 제품 소개서를 받았는데 “정확도 99%”라고만 적혀 있을 때 사용합니다.

첫 화면에 이미 비슷한 문장이 있다면 중복해서 늘리지 말고, 가장 강한 한 문장으로 통합한다.

---

## 2-3. CTA 우선순위를 더 분명하게 한다

처음 방문한 사람에게 가장 중요한 행동은 하나다.

> 예시로 먼저 체험하기

따라서 다음 우선순위를 유지하거나 더 강화한다.

```text
1순위: 예시로 바로 보기
2순위: 소개서 문장 붙여 넣기
3순위: 숫자로 직접 입력
4순위: 기존 검토 파일 열기
5순위: 논문 실험실
```

모든 버튼이 동일한 중요도로 보이면 안 된다.

논문 실험실은 매우 좋은 기능이지만 첫 행동과 경쟁해서는 안 된다.

---

## 2-4. 첫 화면 정보량을 다시 측정한다

현재 Hero에서 동시에 보이는 요소 수와 텍스트 길이를 실제로 측정한다.

가능하면 다음 원칙을 적용한다.

- 메인 메시지
- 쉬운 비유
- 세 단계
- 대표 예시 그림
- 메인 CTA

까지만 첫 화면의 중심으로 두고,

다음은 시각적 중요도를 한 단계 낮춘다.

- 직접 입력
- 소개서 판독
- 검토 파일 열기
- 개인정보 설명
- 논문 링크
- 실험실 링크

삭제하지 말고 **시각적 계층을 명확하게 분리**한다.

# 3. 목표 2 — UI / 정보 구조 10점에 가깝게

## 3-1. 전체 앱을 4개 층으로 재정리해서 검토한다

### 1층 — 이해

- 문제
- 이 앱의 역할
- 예시 체험

### 2층 — 사용

- 소개서 입력
- 숫자 입력
- 평가 조건 질문

### 3층 — 판단 보조

- 결론
- 왜?
- 그래서?
- 공급자 질문

### 4층 — 근거

- 논문 실험실
- 수치 근거
- 규칙 코드
- 연구 한계
- 원문 링크

사용자가 1층에서 4층 내용을 한꺼번에 보지 않도록 한다.

---

## 3-2. 결과 화면의 첫 5초를 더 강하게 만든다

사용자가 결과 화면에 들어오면 가장 먼저 보여야 하는 것은 다음이다.

```text
현재 결론
→ 왜 그런가
→ 다음 행동
```

현재 `ConclusionCard`의 `결론 / 왜? / 그래서?` 구조는 유지할 가치가 높다.

다만 실제 결과 화면을 점검해 다음 문제가 없는지 확인한다.

- 결론 카드보다 다른 정보가 먼저 시선을 뺏는가?
- 한 화면에서 너무 많은 카드가 동시에 보이는가?
- 첫 버튼이 “업체에 물을 질문 보기”로 자연스럽게 이어지는가?
- 사용자가 결과의 의미를 읽기 전에 전문 용어부터 만나지는 않는가?

필요하다면 레이아웃과 시각적 위계를 조정한다.

---

## 3-3. 전문 용어는 숨기지 말고 단계적으로 노출한다

다음 용어는 프로젝트의 강점이므로 제거하지 않는다.

- Macro F1
- FPR
- Attack Recall
- XGBoost
- SHAP
- Jaccard
- CICIDS2017
- unseen attack / 미관측 공격

대신 처음 나올 때는 쉬운 표현을 먼저 둔다.

예:

```text
공격을 실제로 얼마나 잡았는지
Attack Recall
```

또는

```text
처음 보는 공격으로 다시 시험
미관측 공격 스트레스 테스트
```

쉬운 말 → 전문 용어 순서를 지킨다.

---

## 3-4. 모바일을 별도 제품처럼 다시 본다

390px 전후 모바일에서 다음을 직접 확인한다.

- 첫 제목이 너무 길지 않은가
- 첫 CTA가 스크롤 전에 보이는가
- 숫자 / 막대 / 카드가 과밀하지 않은가
- 결론 → 질문까지 흐름이 끊기지 않는가
- 표가 핵심 이해를 방해하지 않는가
- 실험실 네 개가 지나치게 긴 페이지가 되지 않는가

필요하면 모바일에서는 일부 상세 내용을 접기 / 펼치기로 처리하되, 핵심 정보는 숨기지 않는다.

# 4. 목표 3 — 기능 완성도 10점에 가깝게

현재 기능은 이미 많다.

이번에는 기능 숫자를 늘리는 것이 아니라 **실제 사용의 마찰을 제거**한다.

## 반드시 다시 검증할 핵심 사용자 흐름

### 흐름 A — 처음 온 사람

```text
홈
→ 예시로 바로 보기
→ 결론 이해
→ 업체 질문 보기
→ 질문을 실제로 사용할 수 있음
```

### 흐름 B — 실제 소개서 검토

```text
홈
→ 소개서 문장 붙여 넣기
→ 자동 표시 / 판독
→ 빠진 평가 조건 확인
→ 질문 완성
```

### 흐름 C — 숫자 직접 입력

```text
홈
→ 숫자로 직접 입력
→ 질문형 입력 흐름
→ 결과
→ 질문
```

### 흐름 D — 후속 검토

```text
1회차 검토
→ JSON 저장
→ 다시 열기
→ 공급자 답변 반영
→ 이전 결과와 변화 비교
```

### 흐름 E — 논문 근거 확인

```text
결론 또는 판독
→ 관련 실험실 바로 이동
→ 논문 결과 확인
→ 검토 화면으로 복귀
```

위 5개가 모두 자연스러워야 한다.

---

## 4-1. “질문을 만든다”의 마지막 단계가 실제로 유용해야 한다

이 앱의 가장 중요한 산출물은 공급자에게 물을 질문이다.

따라서 질문 화면에서 다음을 확인한다.

- 질문이 우선순위별로 이해되는가
- 왜 물어야 하는지 짧게 설명되는가
- 질문 복사가 쉽고 명확한가
- 여러 질문을 한 번에 복사할 수 있는가
- 회의 / 이메일 / PoC 체크리스트에 바로 붙여 넣을 수 있는가

이미 기능이 있다면 UX를 점검하고, 없다고 해서 무조건 새 기능을 추가하지 않는다.

실제로 사용성을 크게 높일 때만 구현한다.

---

## 4-2. 오류 입력 경험도 제품 품질로 본다

다음을 직접 확인한다.

- 빈 입력
- 0
- 100
- 100 초과
- 음수
- 소수
- 잘못된 혼동행렬
- 서로 모순되는 지표
- 이상한 JSON
- 1 MiB 초과 파일
- 지원하지 않는 형식
- 소개서에 판독 표현이 하나도 없는 경우

오류 메시지는 기술 오류가 아니라 사용자가 **다음에 무엇을 해야 하는지** 알려줘야 한다.

---

# 5. 목표 4 — 포트폴리오 가치 10점에 가깝게

이 프로젝트의 포트폴리오 가치는 기능보다 **문제 해결 과정**에 있다.

아래 이야기가 제품 안과 README에서 자연스럽게 드러나야 한다.

```text
문제
보안 AI 제품은 높은 성능 숫자를 강조한다.

연구
같은 모델도 평가 데이터 분할 방식에 따라 성능과 설명이 크게 바뀌었다.

판단
숫자 자체를 평가하기보다 숫자가 만들어진 시험 조건을 먼저 확인해야 한다.

구현
소개서와 성능표에서 빠진 조건을 찾아 공급자 질문으로 바꾸는 ExplainSOC를 만들었다.

검증
실사용 관찰 → UX 수정 → 자동 테스트 → 배포 검증까지 반복했다.
```

---

## 5-1. 첫 화면 또는 About 영역에서 “논문 → 앱” 연결을 짧고 강하게 보여 준다

현재 논문 링크만 있는 수준을 넘어, 필요하다면 아래와 비슷한 연결을 아주 짧게 보여주는 방법을 검토한다.

> 10번 논문에서 확인한 “평가 방식에 따른 성능 착시”를 실제 제품 검토 질문으로 바꾼 앱입니다.

단, Hero를 더 길게 만드는 방식이면 하지 않는다.

적절한 위치가 없다면 README와 포트폴리오 카드에서 해결한다.

---

## 5-2. 개발자의 판단을 보여 준다

포트폴리오를 보는 사람은 “AI가 만들었다”가 아니라 **개발자가 무엇을 판단했는지** 보고 싶어 한다.

README 또는 사례 설명에서 다음이 드러나게 한다.

- 왜 점수 판정을 하지 않았는가
- 왜 예시 체험을 먼저 두었는가
- 왜 결과를 세 장으로 나눴는가
- 왜 결론 카드를 추가했는가
- 왜 캐릭터를 넣지 않았는가
- 왜 소개서 판독을 규칙 기반으로 했는가
- 왜 입력 데이터를 서버로 보내지 않는가

이미 문서에 충분히 있다면 중복 추가하지 않는다.

대신 포트폴리오에서 읽기 좋은 형태인지 검토한다.

# 6. 목표 5 — 네트워크·보안 직무 연결 10점에 가깝게

ExplainSOC가 단순 프론트엔드 프로젝트로 보이면 안 된다.

- 보안 제품 PoC
- 벤더 성능 주장 검토

## 6-1. SOC / 보안 담당자의 실제 업무 흐름에 연결한다

가능하면 사용자 상황 설명이나 README에서 아래 흐름이 읽혀야 한다.

```text
벤더 제안서 수신
→ PoC 성능표 검토
→ 테스트 조건 확인
→ 탐지율 / 오탐률 확인
→ 미관측 공격 검증 여부 확인
→ 부족한 증거를 질문
→ PoC 추가 검증
```

ExplainSOC가 이 중 **성능표 검토 → 부족한 증거 질문 생성** 구간을 돕는다는 것이 명확해야 한다.

---

## 6-2. 네트워크 보안 데이터라는 점을 더 명확히 설명한다

논문 실험실에서 CICIDS2017을 단순 ML 데이터셋처럼 보이지 않게 한다.

필요하면 한 줄 수준에서 다음을 설명한다.

- 네트워크 트래픽 기반 침입 탐지 데이터셋
- 정상 흐름과 공격 흐름을 분류
- 실제 보안 환경에서는 학습에서 보지 못한 공격이 등장할 수 있음

단, 긴 강의 자료처럼 만들지는 않는다.

---

## 6-3. “SOC 도구”처럼 과장하지 않는다

ExplainSOC는 실제 SIEM, IDS, IPS를 대체하는 제품이 아니다.

다음 정체성이 정확하다.

> 보안 AI 제품의 PoC / 제안서 성능 주장을 검토할 때 사용하는 의사결정 보조 도구

이 경계를 유지한다.

# 12. BRB-C11 성공 기준

이 테스트의 목표는 “좋다는 칭찬 받기”가 아니다.

다음이 중요하다.

- 처음 보는 사람이 1분 안에 목적을 이해한다.
- 설명 없이 핵심 행동을 완료한다.
- 어디서 막히는지 객관적으로 확인한다.

실패하면 실패 기록도 그대로 남긴다.

실패 결과를 숨기지 않는다.

다만 실패 지점이 명확하다면 V10 범위 안에서 가장 작은 수정으로 해결한다.

수정 후에는 **같은 사람에게 답을 알려주고 다시 시험한 결과를 공식 신규 사용자 검증처럼 사용하지 않는다.**

필요하면 ExplainSOC를 보지 않은 다른 사람에게 다시 시험한다.
