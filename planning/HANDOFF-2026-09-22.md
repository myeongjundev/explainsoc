## 1. 학원에서 할 일 — 순서대로

### 1-0. 시작 (10분)

과제 폴더들이 모여 있는 상위 폴더에서 두 저장소를 최신으로 받는다. 집 PC에서 마지막으로 푸시한 커밋은 13번이 이
문서를 올린 커밋, 12번이 `ea77b4e`다.

```bash
git -C t13-explainsoc pull --ff-only
```

```bash
git -C t12-about pull --ff-only
```

폴더가 없으면 새로 받는다.

```bash
git clone https://github.com/myeongjundev/explainsoc.git t13-explainsoc
```

Node는 24.15 이상이어야 한다(22.x라면 22.22.2 이상). 설치와 전체 검사는 다음과 같다.

```bash
node -v
```

```bash
npm --prefix t13-explainsoc ci
```

```bash
npm --prefix t13-explainsoc run verify
```

`verify`가 통과하면 안전 검사 11개, 단위·컴포넌트 91개, 빌드, 브라우저 24개가 모두 초록이다. 브라우저 검사는
**설치된 Chrome**을 쓴다. Chrome이 없으면 `npx playwright install chromium`으로 받은 뒤 환경 변수 `CI=1`을 주고
돌린다(PowerShell: `$env:CI='1'; npm run test:e2e`).

**ZIP은 저장소에 없다.** `release/`가 `.gitignore`에 있어 집 PC에만 있다. 제출할 ZIP을 학원 PC에서 같은 커밋으로
다시 만든다. 커밋을 꼭 적는다. 적지 않으면 지금 커밋(HEAD)으로 만들어 이름과 해시가 달라진다.

```bash
npm --prefix t13-explainsoc run release:zip -- 679add3
```

- 출력의 SHA-256이 `80650a67…ecffdbd`(위 표의 전체 값)와 **같으면** 그대로 제출한다. 다른 PC에서도 같은 해시가
  나왔다는 뜻이라 재현성의 좋은 증거다. `evidence/card-5.md` 제출 목록 아래에 "학원 PC(Git 버전)에서도 같은
  SHA-256" 한 줄을 남긴다.
- **다르면** Git 버전 차이일 수 있다(`git --version`, 집 PC는 2.53.0.windows.2). 파일 내용은 같다. 새 해시를 card-5에
  적고, 5절 절차로 새 임시 폴더 확인을 한 번 한다.

## 5. ZIP을 다시 만들어야 할 때 — 새 임시 폴더 확인 절차

**언제:** ZIP 허용 목록 안의 파일을 바꿨을 때다. 허용 목록은 `README.md`, `LICENSE`, `package.json`,
`package-lock.json`, `.gitignore`, `index.html`, `vite.config.ts`, `tsconfig.json`, `playwright.config.ts`,
`public/`, `src/`, `tests/`, `scripts/`다. `evidence/`, `planning/`, `TROUBLESHOOTING.md`만 바꿨다면 ZIP은 그대로다.

**순서:**

1. 코드를 커밋하고 푸시한다. GitHub Actions가 초록인지 본다(검사 → 배포).
2. `npm run release:zip -- <그 커밋>`을 두 번 돌려 SHA-256이 같은지 본다.
3. 새 빈 폴더에 ZIP을 푼다(Windows 탐색기 "압축 풀기" 또는 PowerShell `Expand-Archive`). `node_modules`, `.git`,
   `dist`가 없는지 본다.
4. 그 폴더에서 `npm ci` → `npm run build` → `npm run preview`를 돌린다. http://127.0.0.1:4173/explainsoc/ 가 200이고
   첫 화면(제목, 도움 문장, 논문 제목, 시작 버튼 둘)이 나오는지 본다.
5. 같은 폴더에서 `npm run check`(11개), `npm test`(91개), `npm run test:e2e`(24개)를 돌린다.
6. `evidence/card-5.md`의 ZIP 이름·크기·SHA-256·원본 커밋과 새 임시 폴더 기록을 고친다. `planning/STATUS.md`도
   고치고, 문서 커밋을 푸시한다(문서는 ZIP에 없으므로 해시가 계속 맞다).
7. 테스트 수가 바뀌었다면 12번 `content/approved.json`의 `t13-app` 검증 칸도 고친다(7절).

## 6. 지켜야 할 것

- 설계 결정 다섯 개(`DESIGN.md` 22절 — 카드 1 문장과 세 행동, 제목, 제품 설명 이름, 9종 대 3종 그림, URL과 ZIP)는
  다시 열지 않는다.
- 설계 밖 기능은 넣지 않는다. 필요하면 적어 두고 결정한 뒤 한다.
- 제출물 어디에도 본인 외 실명·연락처·비밀값을 두지 않는다. 테스트 주석과 증거 문서도 제출물이다. 검사에
  걸리면 검사기를 느슨하게 만들지 않고 내용을 고친다.
- 동료의 감상, 사람이 잰 60초, 제출문 ②는 지어내지 않는다.
- 어느 저장소든 만지기 전에 `git fetch`와 `git status -sb`부터 한다. 집 PC와 학원 PC가 같은 저장소를 쓴다.
- 10번 저장소(`explainsoc-research`)는 제출본이다. 읽기만 한다.
- 12번 저장소는 13번 카드(`t13-app`) 말고는 건드리지 않는다.

## 7. 알려진 위험과 주의

- **공개 주소 캐시.** GitHub Pages가 `Cache-Control: max-age=600`을 보낸다. 배포 뒤 최대 10분은 이전 화면이 보일 수
  있다.
- **12번 카드의 테스트 수.** 현재 사례 노트 검증 칸은 "단위·컴포넌트 테스트 91개와 … 브라우저 테스트 24개"다.
  13번 테스트 수가 바뀌면 12번 `approved.json`을 고치고, `device/build_site.py`로 사이트를 다시 만들고, 12번 검사를
  돌린다.
- **ZIP 해시는 커밋과 Git 버전에 묶인다.** 1-0 참고.
- **12번 제출 문구.** 12번 제출 때 적은 확인 방법의 "13번 앱 예정 자리"와 지금 사이트(공개 카드)가 다르다. 12번
  기록에 적어 둔 제출 뒤 할 일을 한 결과다.
- **스크립트를 끼워 넣는 프로그램이 있는 PC.** fixture 덕분에 테스트는 통과한다. 다만 그 PC의 Chrome으로 공개
  주소를 직접 열면, 앱이 하지 않은 콘솔 오류가 보일 수 있다(앱의 보안 정책이 끼워 넣은 스크립트의 전송을 막은
  기록이다).
- GitHub Pages에서는 `frame-ancestors`를 걸 수 없다. 로그인·저장·전송이 없는 앱이라 받아들였다(card-4).
