## 2. 제품 한 문장과 사용자 행동

> 보안 AI 도입을 처음 맡은 주니어 보안 담당자가 제품 소개서의 성능 숫자 한두 개를
> 받았을 때, 이 앱이 무작위 분할 XGBoost의 Macro F1 0.9979가 미관측 공격 스트레스
> 테스트에서 0.3871로 하락한 논문 결과를 근거로 그 숫자가 말하지 않는 평가 조건과
> 클래스별 오류를 드러내고, 공급자에게 바로 물을 질문을 만들어 준다.

사용자가 할 일은 세 가지다.

1. 받은 성능 숫자 하나를 적거나 `논문 예시로 60초 검토`를 선택한다.
2. 분할 방식, 미관측 공격 포함 여부, 중복 제거 여부에 `예 / 아니오 / 모름`으로 답한다.
3. 숫자가 말하는 것과 말하지 않는 것을 확인하고 공급자에게 물을 질문을 복사한다.

첫 화면 제목은 `그 99%, 무엇을 시험한 점수입니까?`, 제품 설명 이름은
`성능표에 없는 질문`이다.

## 3. 절대 바꾸지 않을 사실과 표현

- 화면의 분할 이름은 **미관측 공격 스트레스 테스트**다. `시간 분할`, `미래 성능`, 순수 시간
  일반화라고 부르지 않는다.
- 정확 혼동행렬은 반올림된 지표에서 역산하지 않는다.
  - 무작위 XGBoost: `[[418934, 362], [220, 84955]]`
  - 미관측 공격 XGBoost: `[[375432, 86], [220628, 160]]`
- 논문 예시 수치는 다음과 같다.
  - 무작위: Accuracy 0.9988, Macro F1 0.9979, 공격 Recall 0.9974, FPR 0.0009
  - 미관측 공격: Accuracy 0.6299, Macro F1 0.3871, 공격 Recall 0.0007, FPR 0.0002
  - 미관측 공격 220,788건 중 탐지 160건
- 항상 정상 기준선 `375,518 / 596,306 ≈ 0.6297`은 IV-3 원수에서 계산한 **화면 설명용
  파생 비교**다. 논문의 새 발견, 합격선, 일반 임계값으로 쓰지 않는다.
- 결과는 CICIDS2017 한 데이터셋에 한정한다.
- Logistic Regression 결과를 `단순 모델이 늘 더 잘 일반화한다`는 결론으로 바꾸지 않는다.
- SHAP은 공격 원인이 아니라 모델 내부 판단의 기여도다. 안정적인 설명은 정확한 탐지를 보증하지
  않는다.
- 실제 SOC 분석가 평가를 했다고 쓰지 않는다.
- 상태 이름은 `입력한 근거 / 확인 필요 / 해석 주의`다. `확인됨`, 합격·불합격, 신뢰 점수,
  자동 추천을 만들지 않는다.

## 4. 구현 순서

### 카드 1 — 기준 고정

- `evidence/card-1.md`에 확정 문장, 세 행동, 승인일을 남긴다.
- DESIGN의 R01~R10, P01~P10을 구현 체크리스트로 옮긴다.
- 첫 구현 커밋 전에 카드 1 증거가 있어야 한다.

### 카드 2 — 작동하는 첫 흐름

- React 19, TypeScript, Vite로 정적 앱을 구성한다.
- 도메인 계산과 검증을 UI보다 먼저 순수 함수로 만든다.
- 논문 예시 60초 경로를 먼저 완주하게 만든다.
- 지표 입력, 2×2 혼동행렬, 세 평가 질문, 주장 뒤집기, 9종 대 3종 정적 그림, 결과와 질문
  복사를 연결한다.
- 잘못된 입력 하나가 전체 결과를 막지 않게 한다.
- 375×812부터 가로 스크롤 없이 동작하고 키보드만으로 완주할 수 있게 한다.
- `evidence/card-2.md`에 화면, 세 행동, 오류 처리, 60초 측정을 남긴다.

### 카드 3 — 데이터와 안전

- 논문 근거와 예시 숫자를 컴포넌트에 흩어 쓰지 말고 데이터 모듈에 둔다.
- 런타임 AI, 백엔드, 분석 도구, 외부 폰트·이미지 요청을 넣지 않는다.
- 입력은 메모리에만 두고 URL, 쿠키, `localStorage`, 로그에 남기지 않는다.
- `.env`와 비밀값이 필요 없음을 README에 명시한다.
- 개인정보·비밀값·외부 호스트·`dangerouslySetInnerHTML` 검사를 자동화한다.
- `evidence/card-3.md`를 남긴다.

### 카드 4 — 공개와 재현

- 모든 단위·컴포넌트·E2E·접근성·프로덕션 빌드를 통과시킨다.
- GitHub Pages에 공개하고 새 시크릿 창에서 로그인 없이 전체 흐름을 확인한다.
- 소스, lockfile, README, 예시 데이터, 테스트, 라이선스만 담은 비밀번호 없는 ZIP을 만든다.
- 새 임시 폴더에서 ZIP을 풀어 `npm ci`, `npm run build`, `npm run preview`를 검증한다.
- `evidence/card-4.md`에 공개 URL, 환경, ZIP 이름과 해시, clean-room 로그를 남긴다.

### 카드 5 — 포트폴리오와 제출

- 공개가 검증된 뒤 T12의 `t13-app` 자리에 URL과 한 문장을 연결한다.
- 처음 보는 동료 한 명의 설명 없는 사용 결과와 이름 없는 한 줄 감상을 받는다. 받을 수 없으면
  지어내지 말고 사용자에게 필요한 행동을 정확히 요청한다.
- 제출 URL·ZIP·확인 방법을 정리한다.
- `AI에게 맡긴 일`, `따르지 않은 제안`의 사실 초안만 제공한다. `내가 직접 판단한 일`은 사용자가
  직접 쓴다.
- `evidence/card-5.md`를 남긴다.

## 5. 구현과 검증 규칙

- 규칙 하나당 단위 테스트를 하나 이상 둔다.
- 정확 혼동행렬 두 개에서 아래 반올림 값이 재현되어야 한다.
  - 무작위: Accuracy 0.9988, Macro F1 0.9979, 공격 Recall 0.9974, FPR 0.0009
  - 미관측: Accuracy 0.6299, Macro F1 0.3871, 공격 Recall 0.0007, FPR 0.0002
- 분모가 0이면 0을 만들지 말고 `계산할 수 없음`을 반환한다.
- `시간 분할`, `미래 성능`, `확인됨`이 제품 화면 문자열에 들어가지 않도록 검사한다.
- BRB-C01~C15와 C22를 모두 증거 파일에 연결한다. 존재하지 않는 C16~C21을 만들지 않는다.
- 기술 난이도가 아니라 작은 완결성과 검증 가능한 증거가 평가 기준임을 잊지 않는다.
- 구현 중 설계 밖 기능을 발견하면 추가하지 않는다. 필요성을 기록하고 사용자 승인을 기다린다.
