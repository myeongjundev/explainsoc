## 3. 다섯 관점의 독립 평가

### 3.1 처음 보는 사람의 이해도

잘된 점:

- 누구를 돕는지: 회사에서 보안 AI 제품 소개서를 검토하는 사람이라는 상황이 있다.
- 무엇을 하는지: 시험 조건을 확인하고 판매 업체에 물을 질문을 만든다는 설명이 있다.
- 첫 행동: `예시로 바로 보기`가 두 화면 크기 모두 초기 화면 안에 보인다.
- 숫자를 준비하지 않아도 시작할 수 있다는 안내가 부담을 줄인다.

남은 위험:

- 제목만 읽으면 제품 성능을 자동 평가하는 앱으로 이해할 수 있다.
- ‘연습문제를 그대로 낸 시험’이라는 비유는 같은 공격 종류와 동일 학습 데이터 재사용을 혼동하게 할 수 있다. 두 개념은 다르다.
- 99.88%는 정확도, 99.8점과 38.7점은 Macro F1을 100배 한 값이다. 설명은 있으나 빠르게 읽으면 같은 지표의 하락으로 오해할 수 있다.

판단 근거: `src/components/Hero.tsx`. 다음 관찰에서는 버튼 발견보다 사용자가 앱의 역할과 숫자를 자기 말로 어떻게 설명하는지 확인한다. 위 위험들을 이유로 지금 첫 화면 전체를 다시 쓰지는 않는다.

### 3.2 UI / 정보 구조

잘된 점:

- 결론 → 왜? → 그래서? 순서가 상세 판독 전에 방향을 잡아 준다.
- `업체에 물을 질문 보기`는 목적지가 명확하다.
- 질문 본문이 규칙 번호보다 강하게 보이고, ‘왜 묻나요’가 바로 아래에 있다.

남은 위험:

- 모바일 결과 화면에서 질문 이동 버튼은 초기 뷰포트 기준 약 y=1,260px에 있었다. 높이 844px 화면에서는 추가 스크롤이 필요하다. 결론만 읽고 사용이 끝났다고 생각할 수 있다.
- 질문 복사 버튼은 답변 상태·메모 영역 아래에 있다. 메모부터 작성해야 한다고 오해하는지 관찰할 필요가 있다.
- 기본 예시의 R01 ‘학습에 없던 공격만 따로 둔 시험 결과’와 R08 ‘미관측 공격만 별도로 둔 스트레스 테스트’ 질문은 의미가 상당히 겹친다.

판단 근거: 공개 UI와 `ConclusionCard.tsx`, `QuestionList.tsx`. 상세 근거가 있다는 이유만으로 반복 영역 전체를 삭제하지 않는다. 실제로 질문에 도달하지 못하는지 먼저 확인한다.

### 3.4 포트폴리오 가치

잘된 점:

- 연구 결과를 실제 검토 질문으로 바꿨다는 연결이 차별점이다.
- 정확도 하나로 판단하지 않기, 모르는 근거를 추정하지 않기, 민감한 입력을 외부로 보내지 않기 등 개발자의 판단이 드러난다.
- 도메인 로직 분리와 재현 가능한 테스트·증거 문서가 구현 신뢰도를 뒷받침한다.

남은 위험:

- 사이트만 2~3분 보면 실험 시각화만 기억하고 개발자의 판단까지는 못 볼 수 있다.
- 테스트 개수를 사용자 이해도의 증거로 내세워서는 안 된다.
- 과거의 여러 관찰을 서로 다른 신규 사용자들이 V10에서 성공한 것으로 해석해서는 안 된다.

면접 핵심 문장:

> 보안 AI의 높은 성능 숫자를 그대로 믿기 전에 시험 조건과 빠진 근거를 확인하고, 공급자에게 물을 질문으로 바꾸는 도구입니다.

### 3.5 네트워크·보안 직무 연결

잘된 점:

- 보안 AI 도입/PoC 단계에서 성능 주장을 검토한다는 역할이 있다.
- 탐지율·오탐률, 미관측 공격, 시험 분할, 중복 여부를 질문으로 전환한다.
- 질문 상태와 답변 메모가 실제 검토 회의에 연결된다.

남은 위험:

- 실제 트래픽을 탐지하거나 SOC 경보를 분석하는 도구로 과장하면 안 된다.
- 연구 결과를 특정 벤더 제품의 실제 성능으로 해석하게 해서도 안 된다.
- ALEPH 동기가 이해할 수 있다는 것과 비전공자가 이해한다는 것은 다르다.

이 프로젝트의 강점은 SOC 전체 구현이 아니라 성능표를 비판적으로 읽고 추가 검증을 설계하는 능력이다.

## 4. 수정 후보 1 — 포함과 별도 검증을 결론에서 구분

**사용자 테스트 전에도 수정할 가치가 있음. 이번 구현 대상.**

### 문제

`src/domain/conclusion.ts`의 `conditionReason()`은 다음 조건을 같은 의미로 취급한다.

```ts
split === 'unseen' || unseen === 'yes'
```

하지만 `unseenIncluded === 'yes'`는 새 공격이 포함됐다는 뜻이지, 새 공격만 따로 평가했고 그 숫자가 별도 평가의 결과라는 뜻은 아니다.

### 재현

아래 입력을 `buildReview()`와 `buildConclusion()`에 전달했다.

```ts
{
  source: 'own',
  claim: { accuracy: 0.99, attackRecall: 0.9 },
  matrix: null,
  split: 'random',
  unseenIncluded: 'yes',
  deduplicated: 'yes',
  claimedBest: 'no',
  claimedExplanation: 'no',
}
```

관찰한 결론:

> 처음 보는 공격으로 시험한 숫자가 있습니다. 아래 숫자를 직접 보고 판단하세요

관찰한 이유:

> AI가 학습 때 보지 못한 종류의 공격으로 따로 시험한 숫자입니다. 처음 보는 공격을 잡는지 볼 수 있는 시험입니다.

전체 시험의 Recall 0.9를 알고 있어도 새 공격만의 Recall을 아는 것은 아니다. 상세 판독은 추가 시험을 질문하는데 상단은 별도 검증을 확인한 것처럼 표현할 수 있다.

### 왜 실제 사용자에게 문제가 되는가

확보하지 못한 증거를 확보했다고 이해해 추가 자료 요청을 생략할 수 있다. 증거 확인 도구의 핵심 신뢰성과 관련된 문제다.

### 어디를 수정하는가

- `src/domain/conclusion.ts`의 시험 조건 해석, 제목 및 이유의 일관성
- 관련 도메인/컴포넌트 회귀 테스트
- 작업 결과 기록이 필요한 기존 상태·인계 문서

### 어떻게 수정하는가

- ‘별도 시험이 확인됨’과 ‘포함됐다는 답만 있음’을 구분한다.
- 포함만 확인된 경우의 의미는 다음 범위를 넘지 않는다: ‘새 공격이 포함됐다는 답은 있지만, 그 공격만의 성능을 따로 확인한 숫자인지는 알 수 없습니다.’
- 이유만 고치고 제목에서는 검증 완료처럼 말하는 상태를 남기지 않는다.
- 전체 시험 숫자는 그대로 표시하되, 새 공격만의 수치라고 연결하지 않는다.
- 입력 스키마·파일 형식·판독 규칙 R01~R15·보안 경계를 불필요하게 바꾸지 않는다.
- 구체적인 내부 구현은 현재 코드에 맞춰 선택하되, 불확실성을 근거 없는 긍정/부정 판정으로 바꾸지 않는다.

### 기대 효과

상단 결론과 상세 질문의 모순을 줄이고, 입력 증거가 보장하는 범위 안에서 설명한다.

### 기존 기능에 미치는 위험

범위를 결론 해석에 한정하면 낮다. 다만 분기 변경에 따라 기존 예시의 제목·이유가 달라질 수 있으므로 모두 확인한다.

### 수정하지 않아도 되는 경우

현재 버전에서 이미 수정됐거나, 해당 입력이 차단되며 ‘예’가 별도 검증까지 보장한다는 사실을 확인한 경우다. 독립 검토 당시에는 그렇지 않았다.

### 최소 회귀 검증

1. `random + yes`: 새 공격만 별도 검증했다고 말하지 않는다.
2. `unknown + yes`: 포함만으로 시험 분할을 확정하지 않는다.
3. `unseen + yes` 및 `unseen + unknown`: 명시적으로 입력된 분할 조건을 불필요하게 잃지 않는다.
4. `unseen + no`: 상충하는 답을 기존처럼 확인 대상으로 남긴다.
5. 공격 Recall 유무 및 혼동행렬 유무에서 제목과 이유가 일관된다.
6. 기존 기본 예시, 미관측 예시, 질문 생성, 파일 왕복 동작에 회귀가 없다.

각 테스트의 세부 기대값은 현재 입력 항목의 정의와 대조해 결정한다. 실제 사용자가 이해했다고 주장하는 테스트는 만들지 않는다.

## 5. 수정 후보 2 — 모바일 질문 이동 노출

**실제 사용자 테스트 결과가 이 문제를 보일 때만 수정. 지금은 구현하지 않는다.**

- 문제: 모바일에서 결론을 읽은 후에도 질문 이동 버튼까지 추가 스크롤이 필요하다.
- 왜 실제 사용자에게 문제가 되는가: 결론을 읽는 것이 끝이라고 생각해 핵심 산출물인 질문을 놓칠 수 있다.
- 어디를 수정하는가: `src/components/ConclusionCard.tsx`와 관련 모바일 스타일.
- 어떻게 수정하는가: 문제가 확인되면 기존 버튼을 모바일에서 결론 제목에 더 가까이 배치한다. 중복 버튼이나 고정 바를 새로 추가하지 않는다.
- 기대 효과: 결론을 본 직후 다음 행동을 발견한다.
- 기존 기능에 미치는 위험: 이유를 읽지 않고 질문으로 이동할 수 있으므로 읽기 순서·키보드 순서·스크린리더 순서를 함께 확인해야 한다.
- 수정하지 않아도 되는 경우: 신규 사용자가 자연스럽게 질문까지 도달하고 결론의 이유도 설명한다면 현재 배치를 유지한다.

## 6. BRB-C11 — 사람이 수행할 신규 사용자 검증

ExplainSOC를 본 적 없는 ALEPH 동기에게 공개 URL만 주고 관찰한다. AI가 발언·시간·익명 평가·성공 여부를 만들어 채우지 않는다.

### 기록할 것

- 검증한 버전, URL, 기기/화면 크기
- 시작 시각과 앱 목적 설명, 예시 실행, 결론 확인, 질문 도달까지의 시간
- 실제 멈춘 위치와 행동, 사용자의 실제 발언
- 도움을 주었다면 그 시각과 안내 내용
- 이름 없는 한 줄 평가
- 도움 없이 성공한 것과 도움 후 성공한 것의 구분

### 중립적인 질문

- 1분 시점: ‘이 사이트가 무엇을 도와주는 것 같나요?’
- 사용 후: ‘결과를 보고 무엇을 알게 됐나요?’
- 사용 후: ‘지금 다음으로 무엇을 하겠나요?’
- 사용 후: ‘이 질문을 왜 해야 한다고 생각하나요?’

### 하면 안 되는 안내

- ‘업체 질문을 만드는 앱인 거 알겠죠?’
- ‘99점만 믿으면 안 된다는 뜻이죠?’
- ‘질문 보기 버튼을 눌러 보세요.’
- 사용자가 막히기 전에 화면 구조나 정답을 설명하는 것

### 수정 필요성을 보여 주는 관찰

- 앱을 제품의 좋음/나쁨 자동 판정기로 설명한다.
- 논문 점수를 입력 제품의 점수로 이해한다.
- 새 공격 포함을 새 공격만의 검증 완료로 이해한다.
- 결론에서 멈추고 질문의 존재를 발견하지 못한다.
- 질문을 찾았지만 왜 묻는지 설명하지 못한다.

`evidence/card-5.md`의 과거 버튼명이나 입력 절차를 현재 V10에 그대로 강제하지 않는다. 기본 예시는 입력 단계를 건너뛴다. 자동 입력 예시에서 사용자가 조건을 직접 입력하지 않았다는 이유로 실패 처리하지 않는다. 과거 관찰을 새 V10 관찰로 다시 적지 않는다.

## 7. 건드리지 않을 부분

- 보안 AI 성능 주장 검토와 공급자 질문 생성이라는 좁은 역할
- 자료 준비 없는 `예시로 바로 보기`

- 질문과 논문/규칙 근거의 연결
- 외부 전송 없는 처리, 명시적 파일 저장, 민감한 숫자를 제외한 질문 복사

- 점수·등급·합격선과 제품 좋음/나쁨 자동 판정을 만들지 않는 원칙

새 백엔드, LLM API, 로그인, 대시보드 확장, 장식용 그래프·캐릭터·애니메이션을 추가하지 않는다. 논문 수치를 바꾸거나 새로운 수치를 만들어 넣지 않는다. 이번 검토의 나머지 관찰 사항을 모두 한 번에 수정하지 않는다.
