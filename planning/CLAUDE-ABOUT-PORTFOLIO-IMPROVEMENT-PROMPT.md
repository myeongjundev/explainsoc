# 김명준 `about/` 포트폴리오 개선 요청 — 프로젝트 수준에 맞게 자기소개를 끌어올리기

## 역할

너는 `myeongjundev/about` 포트폴리오를 검토하는 **Senior Portfolio Designer + Frontend Engineer + Technical Recruiter 관점의 리뷰어**다.

이번 작업의 목표는 사이트를 새로 만들거나 화려하게 리디자인하는 것이 아니다.

현재 프로젝트 결과물, 특히 **ExplainSOC와 T10 네트워크 침입 탐지 연구의 수준에 맞게 포트폴리오의 자기소개·대표작 정보 구조·채용 담당자 동선을 끌어올리는 것**이 목표다.

핵심 정체성은 다음 문장을 기준으로 한다.

> **서비스 개발 경험을 네트워크·보안으로 확장하고 있는 신입 개발자**

이 문장을 그대로 모든 곳에 반복하라는 뜻은 아니다.

사이트 전체가 이 정체성을 자연스럽게 증명하도록 정보 구조와 문장을 정리한다.

---

# 0. 가장 중요한 작업 원칙

## 바로 코드를 수정하지 않는다

먼저 현재 `myeongjundev/about` 저장소를 실제로 읽고 분석한다.

반드시 다음을 먼저 확인한다.

- 현재 실제 배포 구조
- 메인 HTML/CSS/JS 또는 사용 중인 빌드 구조
- `content/approved.json` 등 콘텐츠 원본
- 현재 Hero 문구
- 자기소개/About 영역
- 기술 스택 영역
- 대표작/프로젝트 영역
- ExplainSOC 카드
- T10 논문 카드
- CLOV 카드
- 인증 프로젝트 또는 T07 관련 카드 존재 여부
- 이력서/자기소개서/경력기술서 링크
- GitHub 링크
- 연락 방법
- 모바일 구조
- 접근성
- 현재 자동 검증/테스트 구조
- GitHub Pages 배포 방식

현재 사이트와 실제 코드가 이 문서에 적힌 과거 정보와 다르면 **현재 저장소가 정답**이다.

분석 없이 Hero나 프로젝트 전체를 덮어쓰지 않는다.

---

# 1. 현재 포트폴리오의 핵심 문제

현재 프로젝트 결과물은 강해졌지만, 자기소개가 상대적으로 평범하게 남아 있을 가능성이 있다.

특히 다음과 같은 소개만 전면에 남아 있다면 현재 수준을 충분히 보여주지 못한다.

- Backend Developer
- Spring Boot · REST API
- 꾸준함 · 책임감
- 백엔드 개발자 취업

이 표현들이 틀렸다는 뜻은 아니다.

문제는 현재의 실제 경험을 너무 좁게 설명한다는 것이다.

현재 포트폴리오에서 보여줄 수 있는 경험은 다음과 같이 확장되어 있다.

```text
서비스 개발
├─ Java / Spring Boot
├─ React
├─ REST API
├─ MySQL
├─ 인증 / OAuth2 / JWT
└─ 배포 / Linux / Nginx / Docker

네트워크·보안
├─ VLAN / ACL / VPN 실습
├─ Linux / 서버 보안
├─ 웹 취약점 점검
├─ 인증·접근통제 고민
├─ XAI 기반 네트워크 침입 탐지 연구
└─ ExplainSOC — 보안 AI 제품 성능 주장 검토 도구
```

따라서 현재 포트폴리오는 단순히 "백엔드를 공부하는 학생"보다 다음 성장 흐름을 보여주는 편이 정확하다.

> **서비스 개발 경험을 네트워크·보안으로 확장하고 있는 신입 개발자**

---

# 2. 이번 개선의 최우선 목표

다음 다섯 가지를 동시에 만족시키는 방향으로 개선안을 만든다.

1. 첫 10초 안에 어떤 개발자인지 이해된다.
2. 대표작 3~4개만 봐도 성장 방향이 보인다.
3. 각 프로젝트에서 기술보다 "내가 어떤 판단을 했는지"가 기억에 남는다.
4. ExplainSOC와 T10 논문이 포트폴리오의 시그니처로 연결된다.
5. 채용 담당자가 사이트를 보고 다음 행동을 쉽게 선택할 수 있다.

목표는 "정보를 많이 넣는 것"이 아니다.

목표는 **가장 강한 정보가 먼저 읽히게 하는 것**이다.

# 3. 첫 화면 정체성 재정의

## 현재 검토해야 할 것

Hero가 여전히 다음과 같은 방향인지 먼저 확인한다.

```text
Backend Developer
계획을 코드로 실현하는 개발자
Spring Boot와 React를 공부하고 있습니다.
```

현재 사이트가 이미 달라졌다면 실제 문구를 기준으로 평가한다.

## 원하는 방향

첫 화면에서는 다음 세 가지가 10초 안에 전달되어야 한다.

### A. 지금 누구인가

> 서비스 개발 경험을 네트워크·보안으로 확장하고 있는 신입 개발자

### B. 어떻게 일하는가

구현에서 끝내지 않고:

```text
문제 정의
→ 구현
→ 검증
→ 사용자 피드백
→ 개선
→ 재검증
```

까지 이어가는 사람이라는 점.

### C. 무엇을 보면 되는가

가장 강한 대표작으로 바로 이동할 수 있어야 한다.

예:

- 대표 프로젝트 보기
- ExplainSOC 보기
- 이력서 보기

단, CTA를 너무 많이 경쟁시키지 않는다.

## Hero 문구 원칙

- "열정", "성장", "책임감" 같은 추상어만으로 구성하지 않는다.
- 프로젝트로 증명할 수 있는 문장을 쓴다.
- 보안 전문가인 척 과장하지 않는다.
- 현재 기반은 서비스 개발이고, 네트워크·보안으로 확장하고 있다는 흐름을 유지한다.
- `Backend Developer` 하나로 현재 경험 전체를 제한하지 않는다.

## 후보 방향

아래 문구는 참고용이다. 그대로 복사하지 않아도 된다.

### 방향 A

> **서비스를 만들고, 검증하며, 보안 관점까지 확장하는 개발자**

### 방향 B

> **기능 구현에서 끝내지 않고 검증하고 설명할 수 있는 개발자**

### 방향 C

> **서비스 개발 경험을 네트워크·보안으로 확장하고 있습니다**

Claude가 현재 사이트 구조를 보고 더 좋은 문구가 있다면 제안한다.

단, 사용자 승인 전 실제 Hero 문구를 임의 확정하지 않는다.

# 4. About Me를 프로젝트 수준에 맞게 업그레이드

현재 About 영역이 다음과 같은 세 문장이라면:

- 문제를 끝까지 해결합니다
- 사용자 경험을 고민합니다
- 협업을 책임집니다

핵심 방향은 좋다.

하지만 현재 프로젝트에서 실제로 증명된 행동과 더 직접 연결해야 한다.

## 원하는 구조

각 강점이 추상적인 자기평가가 아니라 **행동 + 증거**로 읽히게 한다.

예:

### 문제를 끝까지 해결합니다

단순히 "끈기 있습니다"가 아니라:

> 인증·배포·브라우저 보안처럼 문제가 여러 계층에 걸쳐 있을 때 원인을 나눠 확인하고, 해결 과정과 재현 방법을 기록합니다.

### 사용자를 보고 고칩니다

> 처음 보는 사용자가 목적을 이해하지 못하거나 결과에서 "그래서 뭐?"라고 한 지점을 기록하고, ExplainSOC의 첫 화면과 결과 구조를 반복 개선했습니다.

### 검증 가능한 결과를 남깁니다

> 기능이 동작하는 것으로 끝내지 않고 브라우저 테스트, 모바일, 키보드 접근, 배포본 검증과 재현 가능한 실행 절차를 남깁니다.

### 협업과 인수인계를 책임집니다

> 팀장 경험에서 역할 분배, Git 흐름, 문서화와 진행 공유를 맡았습니다.

반드시 네 개로 늘리라는 뜻은 아니다.

현재 레이아웃에 가장 맞는 3개 정도로 압축해도 된다.

핵심은 **프로젝트가 증명하는 자기소개**여야 한다.

# 5. 대표작은 3~4개에 집중

프로젝트가 많다고 더 강한 포트폴리오가 되는 것은 아니다.

채용 담당자가 2~3분만 본다고 가정한다.

대표 영역에서는 가장 강한 프로젝트 3~4개에 집중하는 방향을 검토한다.

## 우선 검토할 대표작

### 1순위 — ExplainSOC

이 프로젝트는 현재 대표작 후보 1순위다.

보여줘야 하는 핵심:

```text
문제
보안 AI의 높은 성능 숫자가 어떤 시험에서 나온 것인지 알기 어렵다.

연구 근거
같은 침입 탐지 모델도 평가 방식에 따라 성능과 설명이 크게 달라졌다.

판단
제품을 좋다/나쁘다로 자동 판정하지 않고,
빠진 시험 조건을 확인하고 업체 질문으로 바꾼다.

구현
논문 근거 + 판독 규칙 + 질문 생성 + 실험실 + 사용자 검증

검증
브라우저·접근성·모바일·보안 경계·배포 검증
```

### 2순위 — T10 네트워크 침입 탐지 연구

ExplainSOC 바로 앞이나 뒤에서 서로 연결되도록 검토한다.

```text
T10 연구
왜 성능 숫자를 그대로 믿기 어려운가?
        ↓
ExplainSOC
그러면 실제 제품 검토에서는 무엇을 확인할 것인가?
```

이 연결이 포트폴리오의 가장 강한 시그니처가 될 수 있다.

### 3순위 — CLOV

보여줘야 하는 핵심:

- 팀 프로젝트
- 팀장 경험
- Spring Boot + React
- 인증/서비스 구조
- 배포 경험
- 협업 판단

단순 기능 목록보다 **팀장으로서 무엇을 판단하고 책임졌는지**를 보여준다.

### 4순위 후보 — T07 인증 프로젝트

가능하다면 다음 강점을 보여준다.

- 인증 설계
- Argon2id / bcrypt / JWT / OAuth2 등 선택 고민
- 자원 제약 환경에서 보안과 성능의 균형
- 패스키 검토
- 세션 통제에 대한 판단

현재 사이트에 적합하지 않거나 콘텐츠가 충분하지 않다면 억지로 대표작으로 올리지 않는다.

## 나머지 프로젝트

아이디어 단계, 작은 실습, 초기 프로젝트는 삭제할 필요는 없다.

대표 영역에서 내려서:

- More Works
- Archive
- Other Projects

처럼 한 단계 낮추는 방안을 검토한다.

# 6. 모든 대표작에 “내가 판단한 것”을 한 줄 추가

이번 개선에서 가장 중요한 포인트 중 하나다.

신입 포트폴리오에서는 기술 스택 나열보다 **판단 흔적**이 차별화된다.

각 대표작 카드 또는 상세 내용에서 다음과 같은 한 줄이 보이도록 설계를 검토한다.

```text
내가 판단한 것
```

또는 더 자연스러운 UI 문구:

- 핵심 판단
- 설계 판단
- 내가 결정한 것
- Why this design

## ExplainSOC 예시

> 성능 숫자에 점수나 합격선을 추가하지 않고, 어떤 시험에서 나온 숫자인지 확인한 뒤 부족한 증거를 질문으로 바꾸도록 설계했습니다.

## T10 연구 예시

> 모델 비교 자체보다 데이터 분할 방식이 성능과 XAI 설명 안정성에 어떤 영향을 주는지 검증하는 쪽으로 연구 질문을 좁혔습니다.

## CLOV 예시

실제 프로젝트 기록을 먼저 확인해서 작성한다.

예를 들어 사용자 흐름, 역할 분배, 인증 구조, 배포 등 실제 사용자가 판단한 일을 한 문장으로 압축한다.

## T07 예시

실제 문서와 코드가 근거로 있는 판단만 사용한다.

AI가 추정해서 만들지 않는다.

# 7. Tech Stack은 나열보다 구조화

현재 기술이 한 줄 태그 목록으로만 되어 있다면 다음과 같은 그룹화를 검토한다.

## Development

- Java
- Spring Boot
- React
- REST API
- MySQL
- MyBatis

## Security / Network

- Spring Security
- JWT
- OAuth2
- Linux
- Nginx
- 네트워크·보안 실습 경험

## Engineering / Delivery

- Git / GitHub
- Docker
- CI/CD
- Testing
- GitHub Pages 또는 실제 사용 중인 배포 경험

단, **실제로 경험한 기술만 표시한다.**

단순히 들어본 기술을 추가하지 않는다.

가능하면 각 핵심 기술이 어느 대표 프로젝트에서 사용됐는지 연결되는 UX를 제안한다.

예:

```text
Spring Boot
CLOV · 인증 프로젝트

Security / Network
T10 · ExplainSOC · ALEPH 실습
```

너무 복잡해지면 하지 않는다.

# 8. 채용 담당자의 마지막 행동을 명확하게

사이트를 다 본 사람이 무엇을 해야 하는지 모르면 안 된다.

현재 하단과 상단 CTA를 확인한다.

최종적으로 다음 행동 중 핵심 2~3개가 분명해야 한다.

- 이력서 보기 / 다운로드
- GitHub 보기
- 연락하기

가능하다면 대표작에서도:

- Live Demo
- Repository
- 검증 기록 또는 Case Study

를 명확히 구분한다.

## CTA 원칙

- 모든 버튼을 같은 중요도로 두지 않는다.
- 가장 중요한 행동 하나를 Primary로 둔다.
- 실제 연결되지 않는 가짜 버튼은 만들지 않는다.
- 연락처가 공개되어 있지 않다면 임의 이메일을 만들지 않는다.
- 현재 저장소에 있는 실제 연락 수단만 사용한다.

# 9. ExplainSOC 카드 개선 시 지켜야 할 것

ExplainSOC는 현재 강한 대표작이므로 함부로 재작성하지 않는다.

현재 카드가 이미 다음을 잘 보여준다면 유지한다.

- `LIVE` 상태
- 문제
- 판단
- 구현
- 검증
- 앱 체험
- 저장소
- 검증 기록
- 대표 이미지

## 검증 숫자 표현

테스트 개수 자체를 주인공으로 만들지 않는다.

예:

```text
146 tests / 35 browser tests
```

보다 먼저:

> 모바일·키보드·잘못된 입력·공개 배포·외부 전송 여부를 자동 검증했습니다.

가 읽히는 편이 좋다.

숫자는 증거로 보조한다.

현재 최신 숫자와 배포 기록은 **반드시 ExplainSOC 저장소의 최신 기록을 다시 확인한 뒤 사용한다.**

과거 수치를 복사하지 않는다.

# 10. 디자인 방향

이번 작업은 대규모 리디자인이 아니다.

현재 사이트의 시각적 아이덴티티가 괜찮다면 최대한 유지한다.

## 유지 우선

- 현재 색상 체계
- 타이포그래피
- 카드 디자인
- 기존 애니메이션
- 반응형 구조
- 현재 페이지의 전체 분위기

## 개선 우선

- 정보 우선순위
- Hero 카피
- 자기소개 문구
- 대표작 순서
- 대표작 카드 정보 구조
- 기술 스택 그룹
- CTA

## 피해야 할 것

- 과도한 3D
- 의미 없는 애니메이션
- 장식용 그래프
- 터미널 모양 남발
- 해커 감성만 강조하는 UI
- 네온 효과 과다
- 내용보다 디자인이 앞서는 구조
- 스크롤 길이만 늘리는 섹션 추가

보안 방향성이 생겼다고 포트폴리오 전체를 전형적인 "해킹 사이트"처럼 만들지 않는다.

전문적이고 읽기 쉬운 포트폴리오가 우선이다.

# 11. 모바일과 첫 화면 검증

최소 다음 화면 크기를 확인한다.

- 1440×900
- 1280×800
- 390×844
- 375×812

첫 화면에서 최소한 다음이 보여야 한다.

1. 이름 또는 정체성
2. 어떤 개발자인지
3. 핵심 CTA

모바일에서 가로 스크롤이 없어야 한다.

대표작 카드의:

- 제목
- 한 문장 설명
- 핵심 판단
- 링크

가 읽기 쉬워야 한다.

---

# 12. 채용 담당자 3분 시나리오로 평가

수정 전 반드시 다음 시나리오를 기준으로 현재 사이트를 평가한다.

## 0~10초

채용 담당자가 이해해야 하는 것:

> "서비스 개발을 해왔고, 최근 네트워크·보안으로 확장하고 있는 신입 개발자구나."

## 10~60초

확인해야 하는 것:

- 대표 기술
- ExplainSOC
- T10 연구
- CLOV 또는 주요 서비스 프로젝트

## 1~3분

알아야 하는 것:

- 어떤 문제를 해결했는가
- 본인이 무엇을 판단했는가
- 어떻게 검증했는가
- 협업/팀장 경험이 있는가
- GitHub/이력서/연락으로 어떻게 이어지는가

이 흐름에서 불필요하게 방해하는 요소가 무엇인지 찾아낸다.

---

# 13. 포트폴리오에서 반드시 느껴져야 하는 성장 스토리

사이트 전체를 읽었을 때 다음 성장 흐름이 자연스럽게 느껴지는지 확인한다.

```text
서비스 개발
Spring Boot / React / DB / 인증
        ↓
팀 프로젝트와 배포
CLOV
        ↓
인증·보안 관심 확장
T07 및 보안 학습
        ↓
네트워크·보안 실습
ALEPH
        ↓
연구
XAI 기반 네트워크 침입 탐지
        ↓
연구를 실제 도구로 전환
ExplainSOC
```

모든 단계를 페이지에 그대로 쓰라는 뜻은 아니다.

대표작 선택과 자기소개만 읽어도 이 성장 방향이 느껴지도록 한다.

# 14. 사실성 원칙

포트폴리오이므로 사실을 과장하지 않는다.

다음을 임의로 만들지 않는다.

- 실무 경력
- 실제 기업 도입 사례
- 실제 SOC 운영 경험
- 실제 보안 사고 대응 경험
- 사용하지 않은 기술
- 측정하지 않은 성능
- 존재하지 않는 사용자 수
- 확인되지 않은 테스트 수
- 가짜 후기
- 가짜 채용 성과

`신입 개발자`라는 사실은 약점이 아니다.

대신:

> 무엇을 배웠고 → 무엇을 만들었고 → 어떤 판단을 했고 → 어떻게 검증했는가

를 정확히 보여준다.

---

# 15. 이번 개선에서 하지 말아야 할 것

다음은 사용자 승인 없이 하지 않는다.

- 전체 디자인 전면 재작성
- 프레임워크 교체
- React/Tailwind 등으로 불필요한 마이그레이션
- 새 백엔드 추가
- 로그인/회원가입 추가
- 방문자 분석 도구 추가
- 개인정보 수집
- AI 챗봇 추가
- 프로젝트를 무작정 더 많이 추가
- 포트폴리오와 관련 없는 기능 추가
- 기존 정상 링크 삭제
- ExplainSOC/T10 연결 약화
- 기존 문서 생성 파이프라인 파괴

# 16. 수정 전 먼저 제출할 분석

코드를 수정하기 전에 아래 형식으로 먼저 보고한다.

```markdown
# about 포트폴리오 개선 분석

- 어떤 개발자로 인식되는가
- 문제점

## 2. 현재 자기소개와 실제 프로젝트 수준의 차이
- 잘 맞는 부분

## 3. 대표작 구조
- 현재 대표작 순서
- 유지할 프로젝트
- 대표 영역에서 내릴 프로젝트
- ExplainSOC/T10 연결 상태

## 4. 각 대표작의 판단 흔적

- 부족한 것

## 7. 모바일/접근성/레이아웃 위험

## 8. 추천 수정안
```

승인 전에는 실제 코드/콘텐츠 파일을 수정하지 않는다.
