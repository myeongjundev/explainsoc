## 1. 한 줄 의견

**논문이 밝힌 "점수 착시"를 남의 평가표에 적용해 주는 판독기**로 가는 게 좋다. 논문의 숫자를
보여 주는 앱이 아니라, 논문이 찾은 규칙으로 **사용자가 가져온 숫자를 점검해 주는** 앱이다.
그래야 과제가 말하는 "이렇다 → 그래서 이렇게 도울 수 있다"가 된다.

## 2. 논문에서 앱이 될 수 있는 문장

카드 1은 "논문의 결론에서 결과 하나를 고릅니다"로 시작한다. 원고에서 쓸 수 있는 문장을 원문
그대로 옮긴다.

| 기호 | 위치 | 원문 |
|---|---|---|
| S1 | VII. 결론 첫 문단 | 이 결과는 한 가지 무작위 분할의 높은 성능만으로 미관측 공격 탐지 능력을 판단해서는 안 됨을 보여 주며 |
| S2 | VII. 결론 둘째 문단 | 따라서 안정적인 설명은 정확하거나 유용한 탐지의 보증이 아니다. |
| S3 | VI-3. 운영적 해석 | 운영자는 전체 정확도만 보지 않고 공격 Recall과 혼동행렬을 함께 확인해야 한다. |
| S4 | VI-2. 안정적인 설명과 유용한 탐지는 별개다 | 설명을 운영에 사용할 때는 최소한 성능, 클래스별 오류, 설명 안정성, 특징 변화에 대한 출력 민감도를 함께 확인해야 한다. |
| S5 | V-2. 가설 검증 | 매우 낮은 FPR 0.0002는 좋은 결과처럼 보이지만, 이는 모델이 거의 모든 흐름을 정상으로 예측한 결과이므로 공격 Recall과 함께 읽어야 한다. |
| S6 | V-2. 가설 검증 | 또한 분할 방식에 따라 모델 순위도 달라졌다. |

과제 원문이 든 세 가지 예시 가운데 셋째 — **"어떤 방법을 제안한 논문이라면 그 방법을 누구나
써 볼 수 있게 한 앱"** — 에 이 논문이 가장 잘 맞는다. S3·S4가 바로 "이렇게 확인해야 한다"는
방법이다.

### 앱이 쓸 논문의 숫자

V-2의 표에서 그대로 옮긴다. 앱은 이 숫자를 **비교 기준**으로 쓴다.

| 분할 | 모델 | Accuracy | Macro F1 | 공격 Recall | 정상 Recall | FPR |
|---|---|---:|---:|---:|---:|---:|
| 무작위 | Logistic Regression | 0.8741 | 0.8207 | 0.9721 | 0.8542 | 0.1458 |
| 무작위 | Random Forest | 0.9984 | 0.9972 | 0.9957 | 0.9990 | 0.0010 |
| 무작위 | XGBoost | 0.9988 | 0.9979 | 0.9974 | 0.9991 | 0.0009 |
| 미관측 공격 | Logistic Regression | 0.7468 | 0.6744 | 0.3718 | 0.9672 | 0.0328 |
| 미관측 공격 | Random Forest | 0.6655 | 0.4835 | 0.0972 | 0.9996 | 0.0004 |
| 미관측 공격 | XGBoost | 0.6299 | 0.3871 | 0.0007 | 0.9998 | 0.0002 |

그 밖에 앱이 쓸 수 있는 숫자:

- 무작위 분할 XGBoost는 시험 공격 85,175건 중 84,955건을 잡고 정상 419,296건 중 362건을 오탐했다 (V-2)
- 미관측 공격 분할 XGBoost는 공격 220,788건 중 **160건만** 잡았다 (V-2)
- 원자료 2,830,743건 중 완전 중복이 308,381건, 10.894%였다 (V-1)
- 날짜 분할에서 학습 쪽에도 나타난 시험 행 19,588건을 추가로 뺐다 (IV-3)
- 미관측 공격 분할 XGBoost의 SHAP Top-5는 세 시드에서 Jaccard 1.0000으로 같았지만 공격 Recall은 0.0007이었다 (VI-2)

## 3. 후보 셋

카드 1의 틀 "○○인 사람이 △△할 때 이 앱이 □□을 해 준다"에 맞췄다.

### A. 점수 착시 판독기 — 추천

- **문장:** 보안 AI의 탐지 성능 수치를 보고 믿어도 될지 판단해야 하는 사람이 "정확도 99%" 같은
  숫자를 볼 때, 이 앱이 그 점수가 어떤 조건에서 나왔는지 물어 논문에서 확인한 착시 — 무작위
  분할의 Macro F1 0.9979가 처음 보는 공격에서는 0.3871로 떨어진 것 — 를 짚고 무엇을 더
  물어봐야 하는지 알려 준다.
- **쓰는 결과:** S1, S3, S5, S6 (보조로 S2)
- **할 일 세 가지**
  1. 평가 조건을 고른다 — 분할 방식, 중복 제거 여부, 시험에 학습에 없던 공격이 있었는지
  2. 보고된 숫자를 넣는다 — 정확도나 Macro F1, 공격 Recall, FPR. 모르면 혼동행렬 네 칸
  3. 판독 결과를 본다 — 걸린 착시 목록, 각각이 논문의 어느 결과에서 왔는지, 더 물어볼 질문
- **돕는 사람:** 보안 입문자·학생, 탐지 모델 도입을 검토하는 주니어 보안 담당자, 논문이나 제품
  소개 자료의 숫자를 읽어야 하는 사람
- **약점:** 사용자가 평가 조건을 모르면 판독이 "모름"투성이가 된다. 그래서 "모르면 그것부터
  물어보라"는 것 자체를 결과로 보여 줘야 한다.

### B. 낮은 오탐의 함정 알림

- **문장:** 탐지 모델 결과표를 읽는 보안 입문자가 오탐률이 낮다고 안심할 때, 이 앱이 공격
  Recall과 함께 읽어 "전부 정상으로 찍어서 오탐이 적은 것"인지 가려 준다.
- **쓰는 결과:** S5, S3
- **할 일 세 가지:** 혼동행렬 네 칸을 넣는다 → 지표 다섯 개를 한 화면에서 본다 → 경고를 읽는다
- **약점:** 범위가 좁다. 1분 안에 이해되긴 하지만 A의 판독 항목 하나로 들어간다.

### C. 설명이 같아도 쓸모는 다르다

- **문장:** AI 설명을 보고 모델을 믿으려는 사람이 설명이 매번 같다는 이유로 안심할 때, 이
  앱이 설명 안정성과 탐지 성능을 따로 보여 준다.
- **쓰는 결과:** S2, S4
- **할 일 세 가지:** 설명 Top-5 두 벌을 넣는다 → 일치도(Jaccard)를 본다 → 공격 Recall과 나란히 본다
- **약점:** SHAP을 아는 사람에게만 1분 안에 읽힌다. 처음 온 사람 기준(과제 원문)에 불리하다.

## 4. 추천과 이유

**A를 뼈대로 두고, B와 C는 A의 판독 항목으로 넣는다.**

- A가 논문의 **머리 결론(S1)** 을 쓴다. B·C는 부수 결과다.
- **돕는 사람이 가장 넓다.** 보안 AI를 만드는 사람이 아니라 숫자를 읽는 사람이면 누구나다.
- **1분 안에 읽힌다.** "그 99%, 처음 보는 공격에서도 통할까요?"는 설명이 필요 없다.
- 사용자가 **자기 숫자를 넣는 순간 논문의 규칙이 실제로 쓰인다**(BRB-C04). 논문 숫자를 보여 주기만
  하면 요약본이지 앱이 아니다.
- 판독 항목마다 "이 경고는 논문 V-2의 이 숫자에서 왔다"를 달 수 있어, 앱과 논문이 서로의 근거가
  된다. 12번 사이트 대표작 자리에 논문과 앱이 나란히 놓일 때 그 연결이 보인다.

### 판독 항목 초안 (A 안에 넣을 착시 다섯)

각 항목은 논문의 한 결과에서만 나온다. 논문에 없는 규칙은 만들지 않는다.

| # | 착시 | 걸리는 조건 | 근거 |
|---|---|---|---|
| 1 | 무작위 분할 점수를 새 공격 성능으로 읽음 | 분할이 무작위이거나 모름 | S1, V-2 표 (0.9979 → 0.3871) |
| 2 | 정확도만 봄 | 공격 Recall·혼동행렬이 없음 | S3 |
| 3 | 낮은 오탐의 함정 | FPR은 낮은데 공격 Recall도 낮음 | S5 (FPR 0.0002, Recall 0.0007) |
| 4 | 가장 높은 모델이 늘 가장 좋다고 봄 | 모델 비교를 무작위 분할 하나로만 함 | S6 (XGBoost 1위 → 미관측에서 3위) |
| 5 | 중복을 안 빼고 잰 점수 | 중복 제거·학습/시험 중복 확인을 안 함 | V-1 (10.894%), IV-3 (19,588건) |

설명 안정성(S2·S4)은 사용자가 "설명이 안정적이라서 믿는다"를 골랐을 때 여섯째 항목으로 붙인다.

## 5. 이미 있는 것 — ExplainSOC 프로토타입

**설계 전에 꼭 봐야 한다.** 10번 저장소 `explainsoc-research`의 `frontend/`와 `backend/`에
대시보드가 있다. 논문 VI-3이 "후속 애플리케이션 과제의 출발점으로 보존한다"고 적었고,
`docs/DECISIONS.md`의 **D-003 "ExplainSOC 앱을 마지막 과제 B로 이월"** 이 바로 이 과제로 넘긴
기록이다. D-003은 이때 앱 확장 작업 — **Docker, PCAP 업로드, Kali 데모** — 도 마지막 B까지
멈춘다고 적었다. 본인이 예전에 세워 둔 계획이다.

| 항목 | 내용 |
|---|---|
| 구성 | React 19 · Vite 7 · TypeScript 프론트, FastAPI 백엔드 |
| 화면 넷 | Overview(두 분할 Macro F1과 격차) · Model Comparison · Attack Analysis(Top-5 SHAP·시드 안정성) · Event Detail(정탐·오탐·미탐별 SHAP) |
| 데이터 원칙 | 화면은 수치를 스스로 계산하거나 예시 값을 만들지 않는다. 고정 산출물을 API로 읽는다 |
| 화면 안전선 | SHAP은 인과가 아니라 모델 내부 판단 근거라고 적는다. 날짜 분할을 "미래 성능"이 아니라 "미관측 공격 조건"으로 적는다 |
| 기록 | `docs/DAY-4-REPORT.md` |

### 이걸 어떻게 쓸지에 대한 의견

- **그대로 13번 앱으로 내는 건 권하지 않는다.** 이 대시보드는 논문 결과를 **열람하는** 화면이라,
  과제의 "누구를 어떻게 돕는가"에 답하지 못한다. 연구자가 자기 결과를 둘러보는 도구에 가깝다.
- **백엔드가 있어서 GitHub Pages에 그대로 못 올린다.** 13번은 로그인 없는 공개 URL이 필요하다
  (BRB-C08·C15). 논문 숫자는 고정값이므로 앱에 출처와 함께 넣으면 서버가 필요 없다.
- **가져올 것은 안전선과 문구다.** 위 표의 "화면 안전선" 두 줄은 13번에서도 그대로 지켜야 한다.
- 대시보드의 네 화면은 13번 앱 안에서 **"근거 보기"** 로 남길 수 있다. 판독 결과에서 "이 경고의
  근거"를 누르면 해당 논문 결과로 가는 식이다. 넣을지는 설계에서 정한다.

### D-003에 적어 둔 확장 계획에 대한 의견

- **PCAP 업로드**는 권하지 않는다. 사용자의 실제 네트워크 기록을 받게 되어 개인정보 조건(BRB-C06)과
  부딪히고, 흐름 추출과 모델 추론에 서버가 필요해 공개 URL로 올리기 어렵다. 무엇보다 논문 결과를
  "쓰는" 게 아니라 논문의 파이프라인을 **다시 돌리는** 일이 된다. 논문은 이미 그 모델이 처음 보는
  공격을 거의 못 잡는다고 밝혔다. 그 모델로 사용자 트래픽을 판정해 주면 논문과 반대 방향이 된다.
- **Kali 데모**도 같은 이유로 뒤로 미루는 게 낫다. 공격 도구 시연은 1분 안에 "누구를 어떻게
  돕는가"를 보여 주기 어렵다.
- **Docker**는 실행 묶음(BRB-C09)으로 낼 때만 의미가 있다. 정적 앱으로 가면 필요 없다.
- 이 셋은 본인의 예전 계획이니, 버릴지 뒤로 미룰지는 본인이 정한다.

## 6. 설계에 넘길 조건

과제 원문과 논문의 해석 경계에서 나오는 것만 적는다. 화면 구성이나 기술 선택은 적지 않는다.

### 과제에서 나오는 것

- 첫 화면에 **논문 제목**과 **"이 앱은 누구를 어떻게 돕습니다" 한 문장** (BRB-C03)
  - 논문 제목: 데이터 분할 방식에 따른 XAI 기반 네트워크 침입 탐지 성능과 설명 안정성 분석
- 처음 온 사람이 **설명 없이 할 일 세 가지를 해 볼 수 있어야** 한다 (BRB-C05). 예시 입력을 미리 채워
  두면 첫 방문자가 바로 판독 결과까지 가 볼 수 있다
- **잘못된 입력에도 멈추지 않는다** (BRB-C05). 빈 칸, 음수, 1을 넘는 Recall, 혼동행렬 합이 0,
  숫자가 아닌 글자 같은 것
- 예시 데이터만 쓴다 (BRB-C06). 논문 데이터 CICIDS2017은 공개 데이터이고 개인정보가 아니지만,
  앱에 원자료를 넣을 필요는 없다. 논문의 **집계 숫자**면 충분하다
- 비밀값 없음 (BRB-C07). AI 서비스를 붙이지 않으면 이 조건은 저절로 지켜진다
- 로그인 없는 공개 URL (BRB-C08·C15)

### 논문의 해석 경계에서 나오는 것 — 앱이 과장하지 않으려면

원고 VI-4와 README "해석의 경계"에 있는 내용이다. 앱 문구가 이걸 넘으면 논문을 잘못 옮긴 것이 된다.

- 결과는 **2017년 합성 환경인 CICIDS2017 한 데이터셋**에 한정된다
- 날짜 기반 분할은 **"순수 시간 일반화"가 아니라 "미관측 공격 스트레스 테스트"** 라고 부른다.
  날짜와 공격 유형 변화를 분리하지 못했다
- Logistic Regression이 미관측 공격에서 가장 높았던 것은 **"단순한 모델이 늘 더 잘 일반화한다"는
  증거가 아니다** (VI-1). 판독 4번이 "그러니 단순한 모델을 쓰라"로 읽히면 안 된다
- **SHAP은 공격의 원인이 아니라 모델 내부 판단의 기여도**다 (VI-2)
- 실제 SOC 분석가 평가나 사용성 연구는 하지 않았다 (VI-3)
- 그래서 앱은 **"이 모델은 나쁘다"고 판정하지 않고 "이걸 더 확인하라"고 묻는** 쪽이 논문과 맞는다

## 7. 내가 정하지 않은 것

- 앱이 될 문장 — 본인이 고른다 (카드 1)
